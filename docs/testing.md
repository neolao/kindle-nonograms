# Testing

Run everything with `npm test` (Vitest, workspace-wide). Run a single file with `npx vitest run <path>`.

## Unit tests

Colocated with the source they test (`packages/*/src/**/*.test.ts`), one file per module. These cover the domain logic in `shared` (clue computation, solvability, contrast color, i18n), the page renderers in `site`, and the hydration scripts in `client` — the latter using a per-file `// @vitest-environment jsdom` pragma rather than a global jsdom default, so pure logic elsewhere in the suite stays fast and doesn't need a DOM.

A `hydrate*.test.ts` file never hand-writes its own DOM fixture: it builds one by calling `site`'s real `render*Page()` and extracting the `<body>` (`packages/client/src/htmlFixture.ts`). This means a fixture can never silently drift out of sync with what the static-site generator actually produces — see `.ux/decisions/001-frozen-chrome-blocking-reconciliation.md`.

## Workflow-shape tests

Four root-level `*-workflow.test.ts` files (`deploy-workflow.test.ts`, `pr-check-workflow.test.ts`, `pr-preview-publish-workflow.test.ts`, `sweep-previews-workflow.test.ts`) read the corresponding `.github/workflows/*.yml` file as text and assert on its trigger, step order, permissions, and artifact names. They exist because a CI workflow has no compiler to catch a silently broken trigger or a renamed artifact — these tests are that compiler, locking in the exact shape the rest of the preview/deploy pipeline assumes (see `docs/architecture.md`'s PR preview pipeline section).

## Repository convention tests

- `repo-structure.test.ts` guards a past architectural decision (no `packages/server`, no `dev:server` script) so the pivot to a static site doesn't silently regress.
- `contributing-guide.test.ts` asserts `CONTRIBUTING.md` exists and documents every `Puzzle` field, so a new contributor's puzzle-authoring guide can't drift out of sync with the actual data shape.

## Content tests

`demoContent.test.ts` loads and validates every puzzle file actually committed under `data/puzzles/` (not a fixture) through the same `loadPuzzleSources` the real build uses, and asserts the demo set includes at least one black-and-white puzzle, one multi-color puzzle, and one four-color puzzle — so the bundled examples stay representative as puzzles are added or removed.

## Real-browser verification beyond Vitest

Vitest's jsdom environment cannot render actual pixels, so two pieces are verified against a real browser instead and kept isolated from the rest of the suite:

- `packages/client/src/decodeImageFile.ts` (the puzzle editor's image-decode step) — jsdom has no `<canvas>` pixel backend.
- The `.claude/skills/run-kindle-nonograms/` skill drives a real headless Chromium (via Playwright, since `chromium-cli` isn't available in this environment) to build the site, serve it, and screenshot a live puzzle/library page — useful for confirming a visual change actually renders correctly, which no unit test can do on its own.
