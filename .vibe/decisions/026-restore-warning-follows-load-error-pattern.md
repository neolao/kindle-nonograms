# The "progress couldn't be restored" note follows load-error's plain pattern, not storage-warning's dismiss pattern

**Context:** Backlog item 042 adds a one-time note shown when saved progress for a puzzle no longer matches its current dimensions and is discarded. The play page already has two precedents for a hidden-by-default note revealed by hydration: `[data-role="storage-warning"]` (amber-styled, with its own dismiss button, shown in reaction to a live user action — a failed save) and `[data-role="load-error"]` (a plain, undecorated, non-dismissible status message, shown once at load time for a fact already true when hydration starts).

**Decision:** The new `[data-role="restore-warning"]` note is built exactly like `load-error`: a plain `<p role="status" aria-live="polite" hidden data-i18n="…">`, no dedicated color/border styling, no dismiss control. It is determined synchronously during `readProgress`, before the grid's own layout-fit pass, so no extra re-fit call is needed the way `storage-warning`'s later, action-triggered reveal requires. It can coexist on screen with a later `storage-warning` (e.g. the player fills a cell after load and that save then fails) with no mutual-exclusion or priority logic between the two — each is independent and toggled by its own condition.

**Reason:** This note reports a fact already true the instant the page loads (like `load-error`), not a live outcome of something the player just did (like `storage-warning`). It fires once and never recurs within a page view by construction (the dimension check runs exactly once, during initial hydration), so a manual dismiss control would add an interactive element with nothing left to dismiss after the one moment it matters. Reusing `load-error`'s established shape also avoids inventing a second "amber warning" visual for what is explanatory, not alarming, information — nothing is actually broken.

**Rejected alternatives:** Mirroring `storage-warning`'s dismiss-button treatment for visual consistency between the two "something about storage didn't work" notes — rejected per UX consultation: the near-identical visual/dismiss treatment would make a normal, expected event (the puzzle changed size since last played) read as the same kind of malfunction as a failed write, and the dismiss control would be dead weight given the note can never reappear that view. Suppressing `storage-warning` while `restore-warning` is visible (or vice versa) — rejected as unnecessary coordination for two notes with genuinely independent causes; the chrome panel already tolerates multiple simultaneous notes structurally (load-error/storage-warning/win-banner already exist as siblings), so stacking them is within the page's existing tolerance.
