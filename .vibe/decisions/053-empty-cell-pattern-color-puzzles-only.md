# Empty-cell background pattern, scoped to color puzzles, single-diagonal, new contrast-picked token

**Context:** A color puzzle's grid cell has no background by default (plain white), identical to a cell the player has actually painted with a white palette color — the player can't tell "nothing here yet" from "I put white here".

**Decision:** Give the grid a subtle single-diagonal (45°) repeating-hatch background, built with `repeating-linear-gradient` (the same CSS mechanism already used for the page's body background texture), rendered only for multi-color puzzles (`palette.length > 1`). The gradient is painted once as the whole `<table>`'s own background, not per data cell (`<td>`) — the standard CSS table background-layering cascade (`border-collapse`) already lets a cell's own opaque `background-color`, set client-side exactly as before, mask the table's background locally within just that cell's box, so a painted cell — including one painted white — is always a flat solid fill, never hatched, with no extra client-side bookkeeping. Because it is one continuous gradient rather than one restarting inside every cell, the diagonal lines run unbroken across cell borders. Header cells (`<th>`, clue numbers) get an explicit opaque background of their own so the pattern never bleeds under them. A crossed cell (marked deliberately empty) keeps the pattern visible under its "X" glyph, since it is still "no color" (its own `background-color` stays unset, same as an untouched cell). The stroke color is a new theme token (`patternInk`, `#9483ad`) rather than reusing the existing pale `line`/`panelEdge` tokens.

**Reason:** A single diagonal direction (not a cross-hatch) can never be visually confused with the existing "X" cross-mark glyph. Measuring the existing neutral tokens showed `line` (~1.3:1) and `panelEdge` (~1.4:1) contrast against white — too pale to reliably survive e-ink grayscale/dithering at small cell sizes (10–26px); `patternInk` (~3.4:1 against white, ~6.1:1 against the grid's black border) is chosen specifically to stay legible there without being confused with the border. Scoping to multi-color puzzles matches the brief exactly — a single-color puzzle's one fixed palette color doesn't create the same white/no-color ambiguity.

**Rejected alternatives:** A cross-hatch pattern (rejected — reads as a second "X" and dilutes the existing cross-mark glyph's meaning). Reusing `line`/`panelEdge` for the stroke (rejected — contrast too low, defeats the point of the feature). Applying the pattern to single-color puzzles too (rejected — out of the brief's stated scope, and the ambiguity is different there). Painting the gradient on each `<td>` individually with the client explicitly clearing it via `background-image:none` on fill (the first shape this decision shipped with — rejected once tried for real: each cell's gradient restarts at its own box, so the diagonal lines visibly break at every cell border instead of reading as one continuous texture across the grid; the table-level version both fixes that and needs no client-side `background-image` bookkeeping at all, since the existing `background-color` masking already does the job for free).
