# Static site build orchestrator: shared bundle, explicit clean, versioned asset filename

**Context:** Backlog item 012 needed one pipeline tying together puzzle discovery, the client bundle build, and both page renderers into a single output directory, since the generated pages' script tags use fixed relative paths (`./assets/main.js`, `../../assets/main.js`) that only resolve if everything lands in the same tree.
**Decision:**
1. **One shared client bundle for both page shapes.** `main.ts` is rewritten to simply import `hydratePlayPage.ts` and `hydrateLibraryPage.ts` for their side effects (each already self-invokes and already no-ops harmlessly when its expected markup isn't present — a puzzle page has no `#puzzles-data`, the library page has no `#puzzle-data`). Both renderers keep referencing the same `assets/main.js` path unchanged. This retires `main.ts`'s old `mount()`/`formatClueLine` placeholder (and its test), which was dead relative to any page the generator actually produces.
2. **The orchestrator owns emptying the output directory**, explicitly (`rm` then `mkdir`), before either the client build or page rendering runs — not Vite's own `emptyOutDir`. This guarantees a puzzle removed from the content source also disappears from a rebuilt output, which relying on Vite's step alone would not: Vite only empties what it itself writes into.
3. **The bundle keeps a fixed, unhashed filename** (`assets/main.js`, via `rollupOptions.output.entryFileNames`) since the generator renders HTML separately from the bundle and can't know a content hash ahead of time — but every generated page's script tag now appends `?v=<hash>`, an 8-character hash of the built bundle's own content, computed once per build. This keeps the predictable path the generator needs while still busting a returning browser's cache on every real content change — important on a device with no easy hard-refresh.
4. **The client bundle build reuses `packages/client/vite.config.ts` as its config file**, overriding only `outDir`/`rollupOptions` inline, instead of re-declaring `base`/`target` in the orchestrator — one Kindle-target config, not two that can drift apart.
**Reason:** An ops consultation on the plan flagged the stale-file and cache-staleness risks in 2 and 3 specifically, and the config-drift risk in 4; 1 follows from `hydratePlayPage`/`hydrateLibraryPage` already being designed (see decisions 005, 006) to self-detect and no-op, which makes a single shared bundle strictly simpler than maintaining two separate entry bundles and two script tags per renderer.
**Rejected alternatives:**
- Two separate client bundles, one per hydration script, each renderer pointing at its own — rejected as unnecessary: both scripts are already safe to load unconditionally on every page, so splitting them only adds a second Vite entry point and two paths to keep in sync for no behavioral gain.
- Content-hashed filenames (Vite's default) — rejected because the HTML is rendered in a separate step from the bundle build and has no way to learn the hash Vite would pick without adding a manifest-reading step; the query-string version achieves the same cache-busting outcome without that extra indirection.
- Configuring `npm run preview` to mount under a GitHub Pages project-page subpath, to catch root-relative-path regressions locally — rejected for now: every internal link and asset path the generator emits is already relative by construction (verified by existing tests going back to items 007/008), so there is no root-relative path in the output that a subpath mount would be needed to catch. Revisit only if a future change introduces a root-relative path.
