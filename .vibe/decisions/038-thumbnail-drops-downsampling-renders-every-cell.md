# The library page's revealed thumbnail renders every real cell instead of downsampling

**Context:** The library page's solved/partial-progress thumbnail (`hydrateLibraryPage.ts`) was built by feeding the puzzle's cells through `shared`'s `buildThumbnail`, a nearest-neighbor point-sampler capped to at most 8 cells per axis. This was found too crude for the Product Owner: a colored detail can vanish entirely from the preview whenever its sampled point happens to land on a blank neighboring cell, since point-sampling looks at only one cell per output block and ignores the rest.

**Decision:** `hydrateLibraryPage.ts` no longer calls `buildThumbnail` for this preview. It renders one `.thumb-cell` element per actual puzzle cell (up to the puzzle's real dimensions, e.g. 45×45), with a per-cell pixel size computed once per puzzle as `THUMBNAIL_BOX_PX / max(width, height)` — the same "single scale factor from the longer axis" proportion rule `buildThumbnail` already used, just applied to sizing instead of to sampling. That size is set inline per thumbnail instance rather than as a single shared CSS rule, since it now varies puzzle-to-puzzle instead of being a fixed constant. The computed size is used as an exact (fractional) CSS length, never rounded to a whole pixel — rounding down can collapse a cell to 0px (invisible, reintroducing the exact defect being fixed) and rounding up can overflow the fixed box on any dimension that isn't a clean divisor of it; letting the browser rasterize a fractional CSS length avoids both failure modes. The existing `.thumb` box's fixed footprint, its flex centering (already relied on for a downsampled grid smaller than the box), and the neutral "?" placeholder for an unsolved puzzle are all unchanged.

**Reason:** The Product Owner explicitly rejected any resampling/aggregation algorithm, wanting no cell of the real grid ever merged, dropped, or substituted for another — the direct, simplest way to guarantee that is to not reduce the cell count at all, only the on-screen size of each cell. `shared`'s `buildThumbnail` stays unchanged and is still used by `site`'s PR-preview PNG renderer, a separate, non-player-facing feature whose own reason for downsampling (bounding a bot-posted image's file size) is unrelated to this fix.

**Rejected alternatives:** Rendering via a single `<canvas>` element (one `fillRect` per real cell) instead of one DOM element per cell — would sidestep both the DOM-weight risk of up to ~2000 elements per large-puzzle thumbnail and the sub-pixel rounding question, and was raised as a real option during expert consultation. Rejected for now: the project has no precedent of `<canvas>` verified on the actual Kindle browser for player-facing content (its one existing use, `decodeImageFile.ts`, is a contributor-only editor tool never required to run on Kindle), while DOM-per-cell at this scale is already proven on Kindle by the play page's own puzzle grid (a real `<table>` up to the same maximum dimensions). The novel risk here — many such thumbnails at once on one library page, rather than one grid on one play page — is a genuinely open question the plan's runtime verification checks for; a canvas rewrite is left as a follow-up if that check finds a real problem, rather than adopted preemptively for a risk not yet confirmed on this project's own target browser.
