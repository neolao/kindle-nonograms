# Editor canvas keyboard navigation uses a roving tabindex, restored (clamped) across every grid rebuild

**Context:** The puzzle editor's paint canvas (backlog item 058) had no keyboard support: plain `<td>`s with no `tabindex`, painted only by a delegated click handler. The canvas's `<table>` is fully torn down and rebuilt (`renderGrid()`) on every resize, palette edit, paint, and image import — not just on resize — so any keyboard-navigation scheme has to survive that rebuild or it silently breaks the moment a contributor keyboard-paints a cell.

**Decision:** Exactly one cell is a Tab stop at a time (`tabindex="0"`, every other cell `tabindex="-1"`), matching the standard grid/spreadsheet keyboard pattern. Arrow keys move focus between cells, clamped at the grid's edges (no wraparound); Enter/Space call the exact same paint/erase code path a click already uses (`paintCell` + `paintGridCell`), updating the existing `<td>` in place rather than going through the full `render()` teardown, so keyboard-painting a cell can never destroy its own focus. A single delegated `focusin` listener on the (rebuild-surviving) grid wrapper is the one place that updates which cell is "current" — covering Tab-in, a mouse click, and an arrow-key-driven `.focus()` call alike, so there is one source of truth instead of three. On every `renderGrid()` rebuild, the remembered current-cell coordinates are clamped to the new width/height and re-applied to the new table's cells; if focus was actually inside the grid at the moment of rebuild (checked via `document.activeElement` before the old table is discarded), focus is restored to the clamped cell after it is attached to the document — otherwise the rebuild leaves focus wherever it already was (on the control that triggered it), never stealing it into the grid. The table/rows/cells also carry `role="grid"`/`"row"`/`"gridcell"` on top of the real `<table>`/`<tr>`/`<td>` structure (never flattened to `<div>`s), labelled by the existing "Canvas" section heading via `aria-labelledby`, so a screen reader's own arrow-key browse-mode navigation doesn't collide with the app's, while native row/column position stays exposed. Each cell's `aria-label` states its current content ("Color N" — reusing the exact same 1-based numbering and `data-i18n-aria`/`{number}` retranslation mechanism already used by the palette swatches, see decision 029 and 023 — or "Empty"), recomputed on every paint/erase, not only at initial render, so it can never go stale relative to the visible fill. The focus ring itself is a color-independent double ring (an inset gap in the panel color, then a contrasting inset ring) rather than a single outline, so it stays visible regardless of the arbitrary palette color painted into the focused cell.

**Reason:** Every actual trigger for a *structural* grid rebuild (resize inputs, palette buttons, the import button) already moves focus onto that control before firing, so live DOM focus is essentially never inside the grid at rebuild time for those — but the *remembered* tabbable-cell position must still survive, or a contributor who arrow-navigated to the middle of a large grid, tweaked a palette color, and tabbed back into the canvas would always restart at the top-left cell. A single-cell paint (the hottest path — every Enter/Space/click) is deliberately kept off the full-rebuild path entirely, updating only the painted `<td>`, so the roving-tabindex bookkeeping and focus itself are never at risk on the one action a keyboard user repeats constantly. Keeping the "current cell" bookkeeping in one delegated `focusin` handler (rather than duplicating it in the click handler, the arrow-key handler, and the post-rebuild restore) means a mouse click and a keyboard move can never disagree about which cell is current. Reusing the palette's own "Color N" numbering and retranslation mechanism, instead of inventing per-cell color names, keeps one accessible-naming convention across the whole editor and requires no new palette-naming feature.

**Rejected alternatives:** Giving every cell its own Tab stop (`tabindex="0"` everywhere) — rejected as it would make Tab crawl through an entire large grid one cell at a time to reach the next panel, unlike every native grid widget. Recomputing and reassigning `tabindex="0"` separately inside the click handler, the arrow-key handler, and `renderGrid()` — rejected as three copies of the same bookkeeping that could drift; superseded by the single `focusin`-driven update. Adding `aria-rowcount`/`aria-colcount`, `aria-activedescendant`, or fabricated `aria-rowindex`/`aria-colindex` — rejected as disproportionate to this "Low" priority audit finding and redundant with the position information the native `<table>` structure under `role="grid"` already exposes. Adding Home/End/Page-Up/Page-Down shortcuts for large grids, and giving the active paint color itself (not just each cell) an accessible name — both real usability ideas raised during expert consultation, rejected as out of scope for this item's acceptance criteria (arrow keys + Enter/Space + a state-describing cell label only); left as possible future follow-ups.
