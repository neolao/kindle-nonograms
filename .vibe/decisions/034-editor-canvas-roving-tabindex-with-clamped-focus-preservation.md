# Editor canvas keyboard navigation uses a roving tabindex, restored (clamped) across every grid rebuild

**Context:** The puzzle editor's paint canvas (backlog item 058) had no keyboard support: plain `<td>`s with no `tabindex`, painted only by a delegated click handler. The canvas's own `<table>` is fully torn down and rebuilt (`renderGrid()`) on every resize, palette edit, and image import — not just on resize — so any keyboard-navigation scheme has to survive that rebuild or it silently breaks the moment a contributor keyboard-paints and then, say, adds a palette color.

**Decision:** Exactly one cell is a Tab stop at a time (`tabindex="0"`, every other cell `tabindex="-1"`), matching the standard grid/spreadsheet keyboard pattern. Arrow keys move focus between cells, clamped at the grid's edges (no wraparound); Enter/Space call the exact same paint/erase code path a click already uses (`paintCell` + `paintGridCell`), never a parallel implementation. A single delegated `focusin` listener on the (rebuild-surviving) grid wrapper is the one place that updates which cell is "current" — covering Tab-in, a mouse click, and an arrow-key-driven `.focus()` call alike, so there is one source of truth instead of three. On every `renderGrid()` rebuild, the remembered current-cell coordinates are clamped to the new width/height and re-applied to the new table's cells; if focus was actually inside the grid at the moment of rebuild (checked via `document.activeElement` before the old table is discarded), focus is restored to the clamped cell — otherwise the rebuild leaves focus wherever it already was (on the control that triggered it), never stealing it into the grid. The table/rows/cells also carry `role="grid"`/`"row"`/`"gridcell"` (labelled by the existing "Canvas" section heading via `aria-labelledby`), so a screen reader's own arrow-key browse-mode navigation doesn't collide with the app's.

**Reason:** Every actual trigger for a grid rebuild (resize inputs, palette buttons, the import button) already moves focus onto that control before firing, so live DOM focus is essentially never inside the grid at rebuild time today — but the *remembered* tabbable-cell position must still survive, or a contributor who arrow-navigated to the middle of a large grid, tweaked a palette color, and tabbed back into the canvas would always restart at the top-left cell. Keeping the "current cell" bookkeeping in one delegated `focusin` handler (rather than duplicating it in the click handler, the arrow-key handler, and the post-rebuild restore) means a mouse click and a keyboard move can never disagree about which cell is current.

**Rejected alternatives:** Giving every cell its own Tab stop (`tabindex="0"` everywhere) — rejected as it would make Tab crawl through an entire large grid one cell at a time to reach the next panel, unlike every native grid widget. Recomputing and reassigning `tabindex="0"` separately inside the click handler, the arrow-key handler, and `renderGrid()` — rejected as three copies of the same bookkeeping that could drift; superseded by the single `focusin`-driven update. Adding `aria-rowcount`/`aria-colcount` or a full editable-grid ARIA pattern (selection, `aria-activedescendant`) — rejected as disproportionate to this "Low" priority audit finding; `role="grid"/"row"/"gridcell"` alone already resolves the concrete browse-mode conflict without that added surface.
