# Cross-tab progress sync uses the native `storage` event and touches only the grid and win banner

**Context:** Backlog item 059 — two tabs open on the same puzzle didn't sync; solving it in one tab left the other showing stale progress/banner until a manual reload. Progress is already persisted per-puzzle to `localStorage` (`progressStorage.ts`).

**Decision:** `hydratePlayPage.ts` listens for the browser's native `storage` event (fires automatically in every other same-origin tab on a `localStorage` write, never in the tab that made the write). On a matching key — this puzzle's exact progress key, or `null` meaning a full `localStorage.clear()` — it re-reads progress and repaints every grid cell by mutating existing `<td>` nodes in place (the same `paintCell` helper single-cell taps already use), then refreshes the win banner's visibility/text the same way a tap or Check click already does, re-fitting the grid only on a hidden→visible banner transition. The one-time storage-warning and restore-warning notes are deliberately left untouched by this resync — they report a fact already true at load time or a save outcome scoped to this page view, not a live property of the puzzle's progress, so they keep their existing "revealed once, never re-evaluated" lifecycle.

**Reason:** The native `storage` event needs no new infrastructure (no polling, no `BroadcastChannel`) and by spec never fires back at its own writer, so there is no risk of a tab reacting to its own action. Mutating existing cell nodes in place — never rebuilding the table — matches how every other update in this file already works and avoids any risk of losing DOM-attached state on a cell (a concern flagged during expert consultation, even though the play grid does not currently carry any per-cell focus state). Scoping the resync to the grid and win banner only keeps its blast radius equal to what genuinely changed (the shared, cross-tab progress record) and leaves each of the two one-time notes' own, already-documented lifecycle (`.vibe/decisions/020-...`, `.vibe/decisions/026-...`) as the single source of truth for when they appear, rather than adding a second, competing trigger for either.

**Rejected alternatives:** Polling `localStorage` on an interval — rejected as needless overhead and latency compared to an event the browser already fires for free. `BroadcastChannel` — rejected as an unsupported API on Kindle's old WebKit browser, a hard constraint for this project. Diffing and patching only the cells that actually changed instead of a full repaint — rejected as unnecessary complexity: a full repaint is already cheap at realistic puzzle sizes, and the project's own `paintCell` is idempotent per cell, so a full pass costs nothing beyond a few extra no-op style writes. Hiding the restore-warning note once a cross-tab sync brings in dimension-compatible progress — rejected (an undetermined product decision resolved autonomously) in favor of leaving it as a load-time-only fact, consistent with its documented one-way lifecycle.
