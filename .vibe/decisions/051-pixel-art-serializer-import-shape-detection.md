# Pixel-art-serializer import reuses the single JSON-shape-detection point, checked before the native shape

**Context:** The editor's JSON import (and the static site's build-time puzzle loader) share one detection function, `parsePuzzleSource`, which today distinguishes only two shapes: this project's native `Puzzle` (has a `palette` array) and the sibling `remarkable-nonogram-generator` export (no `palette`, a `cells: boolean[][]` grid instead). A third sibling project, `pixel-art-serializer`, exports a JSON shape that also carries an array field named `palette` (of `{index, color, reserved}` objects, not plain hex strings) plus a flat `pixels: number[]` array and `gridWidth`/`gridHeight` instead of `width`/`height`.

**Decision:** Add `isPixelArtSerializationShape()` (keyed on the unique `pixels` field) and check it *before* `isNativePuzzleShape()` in `parsePuzzleSource`, so a pixel-art file is never misrouted into the native parser just because both shapes happen to have an array called `palette`. The new adapter, `fromPixelArtSerialization()`, drops every palette entry whose `reserved` flag is `true` from the puzzle's palette entirely (never a placeholder color, never a palette slot) and maps every pixel referencing a reserved index to an empty cell (`null`); every other pixel maps to its color's position in the resulting palette. A pixel referencing an index absent from the file's own palette (out-of-bounds `pixels` array included) throws, same "reject rather than guess" posture as `createPuzzle`'s own structural checks. Colors are normalized from the format's 8-digit `#rrggbbaa` hex to this project's strict 6-digit `#rrggbb` by reusing `contrastColor.ts`'s existing `normalizeBackgroundHex` (now exported) rather than writing a second hex-normalizer.

**Reason:** Detection order is the only fix needed for the shape-collision risk, since the three shapes remain otherwise structurally distinct (`pixels` vs `cells`, `gridWidth`/`gridHeight` vs `width`/`height`); no new format tag or explicit discriminant field was worth introducing for a problem detection order already solves. Treating the reserved color as "always absent from the palette, never a slot" matches the same convention the editor's separate image-import panel already uses for its background color, keeping the two color-reduction entry points consistent for anyone using both.

**Rejected alternatives:** A dedicated new UI control (separate file input/button) for this third format — rejected per the UI/UX consultation: a single shared import surface for all three JSON shapes is the existing, working pattern, and splitting it would only fragment it for no user benefit. Enforcing solvability or a palette-size cap on pixel-art import specifically — rejected as inconsistent with the other two JSON formats, neither of which enforces either today (see `.vibe/decisions/040-editor-solvability-diagnosis-and-json-import.md`).
