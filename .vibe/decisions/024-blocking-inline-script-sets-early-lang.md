# A blocking inline `<script>` sets `<html lang>` from the saved cookie before hydration

**Context:** Every generated page hard-codes `lang="en"` at build time (this is a static site generator with no per-request rendering); only `applyLocale()`, run once the deferred `<script type="module">` hydration bundle executes, corrects `document.documentElement.lang` to the visitor's actual resolved locale. A crawler, assistive tech reading the page from the start of a session, or a no-JS/slow-JS view sees `lang="en"` tagged on possibly-French content until hydration finishes.

**Decision:** Add one small, non-module, synchronous inline `<script>` (`renderEarlyLangScript()`, `packages/site/src/earlyLangScript.ts`) placed immediately after `<meta charset>` — first thing in `<head>`, ahead of the `<style>` block and the module bundle — on all three generated page shapes (library, puzzle, editor). It reads the saved locale cookie directly, and if its value is exactly `"en"` or `"fr"` (the shared `SUPPORTED_LOCALES` list), sets `document.documentElement.lang` to it immediately; any other value (missing cookie, unsupported/tampered value, or `document.cookie` throwing) leaves the page's baked-in `lang="en"` default untouched, silently. It deliberately does not also consult `navigator.language` the way the later `resolveLocale()` does — a first-time visitor with no cookie yet still waits for hydration to pick up their browser language, exactly as before.

**Reason:** A classic (non-module) inline script with no `src` runs synchronously the instant the HTML parser reaches it, unlike a `<script type="module">`, which is always deferred until after the whole document is parsed — so this is the earliest point in the page's lifecycle a client-only value (there is no server-side render to know a visitor's locale ahead of time) can affect emitted markup, closing the gap the audit flagged. Scoping it to the cookie alone (no `navigator.language` fallback here) keeps the early script tiny and its one failure mode (a corrupted/inaccessible cookie) trivial to reason about; the existing, unchanged `resolveLocale()`/`applyLocale()` hydration pass already covers the browser-language case a moment later, so nothing regresses for a visitor without a cookie — they're exactly as well served as before this change, just no worse.

**Rejected alternatives:** Also checking `navigator.language` in the early script — rejected as unnecessary duplication of `resolveLocale()`'s own logic for a case the brief doesn't require covering (a visitor's very first, cookie-less page view) and where the existing hydration correction already applies; a `<script type="module">` instead of a classic script — rejected because module scripts are always deferred past the parse, which is exactly the timing this fix needs to beat; moving language resolution to the server — not applicable, this project intentionally ships no backend (`.vibe/index.md`'s "no longer ships a runtime server").
