# Module: site
**Role:** Static-site generator — discovers/validates puzzle content, renders every page, and orchestrates the full build.
**Files:** `packages/site/src/discoverPuzzles.ts`, `packages/site/src/theme.ts`, `packages/site/src/sharedStyles.ts`, `packages/site/src/renderPuzzlePage.ts`, `packages/site/src/renderLibraryPage.ts`, `packages/site/src/htmlEscape.ts`, `packages/site/src/build.ts`, `packages/site/src/build-cli.ts`
**Exports:** `loadPuzzleSources(dir): Promise<Puzzle[]>`, `FONT_STACK`, `LABEL_FONT_STACK`, `COLORS`, `BORDER_WIDTH`, `SPACING_PX`, `MIN_TAP_TARGET_PX`, `BORDER_RADIUS_PX` (`theme.ts`) — plain TS constants: a conservative body-text font stack plus a second monospace `LABEL_FONT_STACK` layered on top for headings/buttons/badges/section labels only (never body copy, where it hurts legibility at Kindle's small sizes); a light paper/panel neutral pair; and the site's three-accent "cabinet" color system — `amber` for navigating away or an active toggle state, `magenta` for the primary in-puzzle action, `teal` for "completed" (shared by the win banner and the library's solved stamp so the two visibly connect), plus decorative-only cycling elsewhere (library row stripes, the marquee dot row) that carries no meaning; deliberately never applied to the puzzle grid's own rendering, so the grid stays the calmest, most legible element on the page (see `.vibe/decisions/013-three-accent-cabinet-reskin.md`); three border widths, a chrome spacing scale separate from the grid's own `em`-based sizing, the minimum touch-target size, and a single corner radius applied everywhere in the cabinet system (panels, buttons, cards, badges, the grid's own frame — purely decorative, so it's layout-inert even on elements the grid-fit calculation cares about) — interpolated into literal CSS strings at build time rather than CSS custom properties, since `var()` support on Kindle's old WebKit is uncertain — same pattern as the palette-driven `.run-cN` classes below, `sharedStyles(): string` — the CSS fragment shared by both page renderers, built from `theme.ts`'s tokens: a subtly paper-textured page background, a duotone-shadow page heading, the decorative dot-row and rule-flanked section-label styles, the `.page-header` row — on the puzzle page, the heading itself joins this row (`flex:1;min-width:0`, its own margin zeroed, `overflow:hidden;white-space:nowrap;text-overflow:ellipsis` so a long puzzle name truncates instead of colliding with or pushing the controls) — the back-link sits before the heading as a compact icon-only control, and a `.page-header-controls` cluster (holding the language switcher, joined there client-side) sits after it, wrapping to its own line on narrow screens — button styling (reused as-is by the back-link via a shared `button,.back-link` selector, colored by accent role, and given a chunky 3D bevel — an offset `box-shadow` that flattens via a discrete style swap on `:active`/`aria-pressed="true"`, never a `transition`) including a visible `:focus` outline and a thicker amber border on `[aria-pressed="true"]`, the language-switcher layout, the `.play-toolbar` button-grouping layout, a `.fill-color-group` sub-container (a lighter, unshadowed bordered box nesting inside the toolbar — reusing `panelEdge`/`paper` rather than `border`/`panel` so it reads as a subtle sub-grouping cue, not a second competing panel) that `hydratePlayPage.ts` wraps around the Fill button and its color swatches so the two visually read as one action, distinct from Cross/Check, the library page's bordered/shadowed/rounded `.panel` wrapper, and a `.sr-only` utility (the standard clip-based visually-hidden-but-accessible pattern) for an icon control's full name — every rule targets an individual chrome element rather than `body`, so the puzzle page's `.grid-wrapper` stays free of any added margin/padding (see `.vibe/decisions/011-chrome-padding-excludes-grid-wrapper.md`); the paper texture and panel box-shadow add zero layout footprint, so they can't affect that measurement either, `renderPuzzlePage(puzzle, assetVersion?): string`, `renderLibraryPage(puzzles: Puzzle[], assetVersion?): string` — visible markup shows only id/name/size per puzzle, but every puzzle's full data (including its solution) is also embedded as JSON so client hydration can check saved progress for a correct solve; the heading, empty-state message, and every solved badge each carry a `data-i18n` key so the client-side language switcher can retranslate them (the server-rendered text itself is always the English default, since there is no per-request rendering to know a visitor's locale ahead of time); `renderPuzzlePage` additionally wraps its `.page-header` row — a compact icon-only "back to puzzle list" `<a href="../../">` link (plain server-rendered markup, so it works even before hydration runs or with JS disabled) before the heading, showing only an aria-hidden "←" glyph while its full translated name (`data-i18n="play.backToLibrary"`) lives on a nested `.sr-only` span — visually hidden (a standard clip-based technique, never `display:none`/`visibility:hidden`, which would also remove it from screen readers) but still announced by assistive tech and still updated in place by the same generic `applyLocale` walker as any other `[data-i18n]` element — plus the heading and the (initially empty) `.page-header-controls` cluster — in a static `.chrome-panel`; deliberately renders no decorative dot-row on this page at all (unlike the library page), since real measurement showed this page's header chrome eating over a third of a small Kindle-sized viewport's height before the grid even started — a bordered/shadowed/rounded box that `hydratePlayPage.ts` also inserts the toolbar/win banner into once built — and gives `.grid-wrapper` its own separate bordered/rounded "screen" frame (`box-sizing:border-box` so neither the border nor the corner radius can push it past its JS-set `max-width`/`max-height` cap), never nested inside `.chrome-panel` or sharing a padded container with it (padding there would break the grid-fit measurement — see `.vibe/decisions/014-puzzle-page-chrome-panel-wrapper.md`); `renderLibraryPage` styles each puzzle row as its own separate bordered/rounded/shadowed card (not a continuous list) with a colored top stripe cycling through the three accents purely as decoration, its row link in the label monospace font with its text vertically centered (`display:flex;align-items:center`), truncated with an ellipsis rather than wrapped (`min-width:0` again required for the ellipsis to actually take effect inside a flex item, same gotcha as the puzzle page's heading), and given an explicit neutral text color plus `text-decoration:none` so it never picks up the browser's default underline or a different `:visited` color, its `.solved-badge` as a bordered, rounded, fixed-rotation stamp colored with the "completed" accent, and reserves a fixed-size `.thumb` placeholder (a neutral "?" glyph, never the puzzle's own solution) in every row for `hydrateLibraryPage.ts` to replace with a real preview once that puzzle is solved; the puzzle page's `.grid-wrapper` is `overflow:hidden` rather than a scrolling container — see `modules/client.md`'s `fitGrid`/`hydratePlayPage` note for why that only actually clips instead of silently growing the page, `escapeHtml(text): string`, `embedJson(value): string` — serializes a value for safe embedding in a `<script type="application/json">` tag, escaping `<` so an embedded `</script>` can't break out, `versionQuery(assetVersion?): string` — formats an optional asset version as a `?v=` suffix, `buildSite({ puzzlesDir, outDir }): Promise<void>` — discovers/validates puzzles first (fail-fast before writing anything), wipes and recreates `outDir` itself, builds the client bundle via Vite's programmatic API at a fixed `assets/main.js` path, then writes the home page and one page per puzzle, all referencing the bundle with the same content-hash-derived version query string
