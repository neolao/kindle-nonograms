# Module: site
**Role:** Static-site generator — discovers/validates puzzle content, renders every page, and orchestrates the full build.
**Files:** `packages/site/src/discoverPuzzles.ts`, `packages/site/src/theme.ts`, `packages/site/src/sharedStyles.ts`, `packages/site/src/renderPuzzlePage.ts`, `packages/site/src/renderLibraryPage.ts`, `packages/site/src/renderEditorPage.ts`, `packages/site/src/htmlEscape.ts`, `packages/site/src/build.ts`, `packages/site/src/build-cli.ts`, `packages/site/src/renderPuzzlePreview.ts`, `packages/site/src/renderPreviewArtifact.ts`, `packages/site/src/render-preview-artifact-cli.ts`, `packages/site/src/previewFilenameGuard.ts`, `packages/site/src/previewComment.ts`, `packages/site/src/previewPrTrust.ts`, `packages/site/src/previewPublishDecisions.ts`, `packages/site/src/previewBranchGit.ts`, `packages/site/src/publish-preview-cli.ts`
**Exports:** `loadPuzzleSources(dir): Promise<Puzzle[]>` — beyond structural validation, also rejects (fail-fast, naming the file) any puzzle that fails `shared`'s `checkSolvability` (requires guessing) or that `findDuplicatePuzzle` matches against an earlier file in the same directory listing, `FONT_STACK`, `LABEL_FONT_STACK`, `COLORS`, `BORDER_WIDTH`, `SPACING_PX`, `MIN_TAP_TARGET_PX`, `BORDER_RADIUS_PX` (`theme.ts`) — plain TS constants: a conservative body-text font stack plus a second monospace `LABEL_FONT_STACK` layered on top for headings/buttons/badges/section labels only (never body copy, where it hurts legibility at Kindle's small sizes); a light paper/panel neutral pair; and the site's three-accent "cabinet" color system — `amber` for navigating away or an active toggle state, `magenta` for the primary in-puzzle action, `teal` for "completed" (shared by the win banner and the library's solved stamp so the two visibly connect), plus decorative-only cycling on the marquee dot row alone, which carries no meaning (the library row stripe no longer cycles through these accents — see below); deliberately never applied to the puzzle grid's own rendering, so the grid stays the calmest, most legible element on the page (see `.vibe/decisions/013-three-accent-cabinet-reskin.md`); three border widths, a chrome spacing scale separate from the grid's own `em`-based sizing, the minimum touch-target size, and a single corner radius applied everywhere in the cabinet system (panels, buttons, cards, badges, the grid's own frame — purely decorative, so it's layout-inert even on elements the grid-fit calculation cares about) — interpolated into literal CSS strings at build time rather than CSS custom properties, since `var()` support on Kindle's old WebKit is uncertain — same pattern as the palette-driven `.run-cN` classes below, `sharedStyles(): string` — the CSS fragment shared by both page renderers, built from `theme.ts`'s tokens: a subtly paper-textured page background, a duotone-shadow page heading, the decorative dot-row and rule-flanked section-label styles, the `.page-header` row — on the puzzle page, the heading itself joins this row (`flex:1;min-width:0`, its own margin zeroed, `overflow:hidden;white-space:nowrap;text-overflow:ellipsis` so a long puzzle name truncates instead of colliding with or pushing the controls) — the back-link sits before the heading as a compact icon-only control, and a `.page-header-controls` cluster sits after it, wrapping to its own line on narrow screens — a reserved, currently-empty extension slot on both this page and the editor page, since neither has anything client-side to join it into (the language switcher moved to the library page's own footer — see `.vibe/decisions/019-library-footer-relies-on-flex-wrap-not-media-queries.md`) — button styling (reused as-is by the back-link via a shared `button,.back-link` selector, colored by accent role, and given a chunky 3D bevel — an offset `box-shadow` that flattens via a discrete style swap on `:active`/`aria-pressed="true"`, never a `transition`) including a visible `:focus` outline and a thicker amber border on `[aria-pressed="true"]`, the language-switcher layout, the `.play-toolbar` button-grouping layout, a `.fill-color-group` sub-container (a lighter, unshadowed bordered box nesting inside the toolbar — reusing `panelEdge`/`paper` rather than `border`/`panel` so it reads as a subtle sub-grouping cue, not a second competing panel) that `hydratePlayPage.ts` wraps around the Fill button and its color swatches so the two visually read as one action, distinct from Cross/Check, the library page's bordered/shadowed/rounded `.panel` wrapper, and a `.sr-only` utility (the standard clip-based visually-hidden-but-accessible pattern) for an icon control's full name — every rule targets an individual chrome element rather than `body`, so the puzzle page's `.grid-wrapper` stays free of any added margin/padding (see `.vibe/decisions/011-chrome-padding-excludes-grid-wrapper.md`); the paper texture and panel box-shadow add zero layout footprint, so they can't affect that measurement either, `renderPuzzlePage(puzzle, assetVersion?): string`, `renderLibraryPage(puzzles: Puzzle[], assetVersion?): string` — visible markup shows only id/name/size per puzzle, but every puzzle's full data (including its solution) is also embedded as JSON so client hydration can check saved progress for a correct solve; the heading, empty-state message, and every solved badge each carry a `data-i18n` key so the client-side language switcher can retranslate them (the server-rendered text itself is always the English default, since there is no per-request rendering to know a visitor's locale ahead of time); ends with a static `<footer class="page-footer">` — a `.page-footer-links` group holding the existing "Create a puzzle" link and a link to the project's `CONTRIBUTING.md` on GitHub (`target="_blank"`/`rel="noopener noreferrer"`, a trailing "↗" glyph plus wording naming GitHub explicitly, since the site never conveys meaning by color alone), into which `hydrateLibraryPage.ts` prepends the language switcher — the only page that still gets one (see `.vibe/decisions/019-library-footer-relies-on-flex-wrap-not-media-queries.md`); `renderPuzzlePage` additionally wraps its `.page-header` row — a compact icon-only "back to puzzle list" `<a href="../../">` link (plain server-rendered markup, so it works even before hydration runs or with JS disabled) before the heading, showing only an aria-hidden "←" glyph while its full translated name (`data-i18n="play.backToLibrary"`) lives on a nested `.sr-only` span — visually hidden (a standard clip-based technique, never `display:none`/`visibility:hidden`, which would also remove it from screen readers) but still announced by assistive tech and still updated in place by the same generic `applyLocale` walker as any other `[data-i18n]` element — plus the heading and the (initially empty) `.page-header-controls` cluster — in a static `.chrome-panel`; deliberately renders no decorative dot-row on this page at all (unlike the library page), since real measurement showed this page's header chrome eating over a third of a small Kindle-sized viewport's height before the grid even started — a bordered/shadowed/rounded box that `hydratePlayPage.ts` also inserts the toolbar/win banner into once built — and gives `.grid-wrapper` its own separate bordered/rounded "screen" frame (`box-sizing:border-box` so neither the border nor the corner radius can push it past its JS-set `max-width`/`max-height` cap), never nested inside `.chrome-panel` or sharing a padded container with it (padding there would break the grid-fit measurement — see `.vibe/decisions/014-puzzle-page-chrome-panel-wrapper.md`); `.grid-wrapper` itself sits inside a `.grid-center` wrapper (`text-align:center`) with `.grid-wrapper` set to `display:inline-block` — the classic shrink-wrap-then-center technique, chosen over `width:fit-content`/`margin:auto` or CSS Grid/Flexbox centering since `inline-block` + `text-align` has the longest track record on old WebKit; this only redistributes existing slack around the already JS-capped box, so it doesn't add any pixel value that the viewport-based fit measurement would need to account for, keeping it compatible with `.vibe/decisions/011-chrome-padding-excludes-grid-wrapper.md`'s constraint; `renderLibraryPage` styles each puzzle row as its own separate bordered/rounded/shadowed card (not a continuous list) with a top stripe that reflects the puzzle's own palette rather than cycling by position — a literal solid black for a monochrome puzzle, or equal-width hard-stop segments (one per palette color, in palette order) for a multi-color one, generated as one `.stripe-N` CSS rule per card (`background-image: linear-gradient(...)`, kept confined to the top band via a shared `background-size`/`background-position` rule on `li`, `border-top-color` left transparent but still 6px wide so the layout footprint is unchanged); every palette hex is checked against a strict `#rgb`/`#rrggbb`/`#rrggbbaa` pattern before being interpolated, falling back to black otherwise, since this page folds every listed puzzle's palette into one shared `<style>` block (unlike the puzzle page's single curated puzzle) — see `.vibe/decisions/015-library-card-stripe-reflects-palette.md`, its row link in the label monospace font with its text vertically centered (`display:flex;align-items:center`), truncated with an ellipsis rather than wrapped (`min-width:0` again required for the ellipsis to actually take effect inside a flex item, same gotcha as the puzzle page's heading), and given an explicit neutral text color plus `text-decoration:none` so it never picks up the browser's default underline or a different `:visited` color, its `.solved-badge` as a bordered, rounded, fixed-rotation stamp colored with the "completed" accent, and reserves a fixed-size `.thumb` placeholder (a neutral "?" glyph, never the puzzle's own solution) in every row for `hydrateLibraryPage.ts` to replace with a real preview once that puzzle is solved; each row also carries `shared`'s `puzzleSizeBucket(puzzle)`/`isMultiColorPuzzle(puzzle)` result as `data-size-bucket`/`data-color-type` attributes, which `hydrateLibraryPage.ts`'s size/color filter controls read directly rather than re-deriving them from the embedded puzzle JSON; the puzzle page's `.grid-wrapper` is `overflow:hidden` rather than a scrolling container — see `modules/client.md`'s `fitGrid`/`hydratePlayPage` note for why that only actually clips instead of silently growing the page, `renderEditorPage(assetVersion?): string` — a pure function producing the puzzle editor page's static shell, a contributor-facing authoring tool distinct from the other two pages: there is no puzzle to render yet, so this only lays out the chrome (back-link, heading) and a set of empty, `data-role`-tagged containers (`editor-width`/`editor-height`, `editor-palette`, `editor-toolbar`, `editor-grid-wrapper` inside a `.grid-center`/`.grid-wrapper` pair styled the same as the puzzle page's own grid frame, `editor-name`/`editor-filename`, `editor-export`, and a reserved, always-present `editor-error` region) that `hydrateEditorPage.ts` (see `modules/client.md`) fills in and wires up client-side. Also statically renders the "import image" panel's own controls (`editor-import-file` — `<input type="file" accept="image/png,image/jpeg">`, `editor-import-palette-size` — a number input capped `max="16"`, `editor-import-background` — a native `<input type="color">`, `editor-import-button`), already-formed inputs rather than empty containers (same pattern as the width/height/name/filename controls) since `hydrateEditorPage.ts` only wires listeners onto them, never builds their markup. Deliberately never renders a `<table>` or either other page's own embedded `#puzzle-data`/`#puzzles-data` script, so it can never be mistaken for the play or library page shape by their own self-detection checks (see `modules/client.md`'s `main.ts` note on import order). `renderLibraryPage` links to it (`editor/`, shown even when the library is empty) via a `library.createPuzzleLink`-keyed link, `escapeHtml(text): string`, `embedJson(value): string` — serializes a value for safe embedding in a `<script type="application/json">` tag, escaping `<` so an embedded `</script>` can't break out, `versionQuery(assetVersion?): string` — formats an optional asset version as a `?v=` suffix, `buildSite({ puzzlesDir, outDir }): Promise<void>` — discovers/validates puzzles first (fail-fast before writing anything), wipes and recreates `outDir` itself, builds the client bundle via Vite's programmatic API at a fixed `assets/main.js` path, explicitly passing `publicDir: packages/client/public` (Vite's own default resolves against `root`, which defaults to `process.cwd()` — not this config file's directory — so leaving it unset would silently copy nothing from that folder, dropping `favicon.svg` from every build; see `.vibe/backlog/done/028-add-a-favicon.md`), then writes the home page, the editor page (`editor/index.html`), and one page per puzzle, all referencing the bundle with the same content-hash-derived version query string and each linking that same favicon at the right relative depth for their own page (`./favicon.svg`/`../favicon.svg`/`../../favicon.svg`)
**PR preview pipeline** (see `.vibe/backlog/done/025-automatic-puzzle-preview-on-pull-requests.md`, `.vibe/decisions/018-pr-preview-trusts-only-workflow-expressions.md`): `loadPuzzleFile(filePath, id): Promise<Puzzle>` — `discoverPuzzles.ts` now also exports its per-file loader directly, reused to load only the specific files a PR's diff names rather than a whole directory. `renderPuzzlePreviewPng(puzzle, options?): Buffer` — a pure PNG encoder built on nothing but `node:zlib` (`deflateSync` + the native `crc32`), no image/canvas dependency: one solid `cellPx`×`cellPx` block per cell in its palette color, fully transparent for `null`; a puzzle whose grid exceeds `maxGridDimension` is downsampled first via `shared`'s `buildThumbnail`, capping the worst-case image size regardless of a submitted puzzle's claimed dimensions. `renderPreviewsForFiles(puzzlesDir, filenames): Promise<{manifest, images}>` (`renderPreviewArtifact.ts`) renders one PNG per requested file via the above two; `render-preview-artifact-cli.ts` is the thin CLI `pr-check.yml`'s `validate` job runs it through, writing `pr-number.txt`/`manifest.json`/`<id>.png` into an artifact directory. `sanitizePuzzleId(entry): string | undefined` (`previewFilenameGuard.ts`) is the allowlist (word chars/dash/dot only, must end `.json`) every manifest filename read back by the privileged workflow passes before it can become a filesystem path. `PREVIEW_COMMENT_MARKER`, `buildPreviewCommentBody({images})`, `buildPreviewRemovedCommentBody()` (`previewComment.ts`) build the sticky PR comment body (a hidden marker so a re-run edits the same comment) for the render and cleanup cases respectively. `isPrNumberAssociated(candidate, associatedPrNumbers)` (`previewPrTrust.ts`) is the trust-chain check: the PR number an artifact declares is only acted on once independently confirmed against GitHub's own commit→PR association. `determineArtifactMode(entries)`, `findExistingPreviewComment(comments)`, `shouldSkipClosedPr(mode, prState)`, `buildRawPreviewImageUrl({owner, repo, prNumber, puzzleId})` (`previewPublishDecisions.ts`) are the remaining small, independently-tested decisions the privileged publish script wires together — respectively: render vs. cleanup artifact detection from its actual downloaded contents, finding the existing marked comment to edit, skipping a render publish for a PR that's already closed (guards against a late `workflow_run` resurrecting an already-cleaned-up preview), and the `raw.githubusercontent.com` URL a pushed image is linked through. `ensureBranchCheckout(repoDir, remoteUrl, branch)`, `writePreviewFiles(repoDir, prNumber, images)`, `removePreviewDir(repoDir, prNumber)`, `listPreviewDirs(repoDir)`, `commitAndPush(repoDir, branch, message)` (`previewBranchGit.ts`) do the actual `git` work against the orphan `puzzle-previews` branch — `writePreviewFiles`/`removePreviewDir` both guard `git add -A -- <pathspec>` (which hard-errors when the pathspec matches nothing, e.g. an already-fully-staged deletion) behind a try/catch rather than a `git status` pre-check, since status can report something "pending" that `add` still has nothing left to do for; `listPreviewDirs` lists every `pr-<n>` directory name under `previews/`, returning `[]` (never throwing) when that folder doesn't exist yet. `publish-preview-cli.ts` is the privileged workflow's own thin script wiring all of the above together with the actual GitHub REST calls (commit→PR association, PR state, list/create/update a comment) and `git` push — the only piece of this pipeline not exercised against real GitHub in this project's own test suite, which instead exercises `previewBranchGit.ts` against a real local git remote (a bare repo on disk) and every decision function directly.

**Scheduled preview sweep** (see `.vibe/backlog/done/032-scheduled-sweep-for-orphaned-puzzle-previews.md`) — an independent backstop for the event-driven cleanup above, not a replacement for it: `computeOrphanedPreviewNumbers(previewPrNumbers, openPrNumbers)` (`previewSweepDecisions.ts`) is a plain set difference — the preview PR numbers with no matching open PR; `parsePreviewDirName(name)` parses a `previews/` entry into its PR number, `undefined` for anything not exactly `pr-<digits>` (a stray/malformed directory is skipped, never misread as PR `NaN`). `sweep-previews-cli.ts` is the thin script `.github/workflows/sweep-previews.yml` (daily `on: schedule` + manual `workflow_dispatch`) runs: lists every open PR via `GET /repos/{owner}/{repo}/pulls?state=open` (paginated) *before* checking out the branch — deliberately, so a preview rendered in the gap between the two reads can only ever be read as still-open, never swept by mistake — diffs that against `listPreviewDirs`'s result, removes every orphan via `removePreviewDir`, and pushes once with all of them in a single combined commit via `commitAndPush`; returns before ever calling `commitAndPush` when nothing is orphaned, so a clean run pushes nothing and never even creates the branch on the remote if it didn't already exist. Tested the same way as the rest of this pipeline: the two decisions directly, and the full sweep (seed several preview dirs, sweep against a given open-PR list, assert only the orphaned ones are removed in one commit) against the same real local bare-repo harness `previewBranchGit.test.ts` already uses.
