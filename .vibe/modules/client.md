# Module: client
**Role:** Vanilla TypeScript frontend, built with Vite (es2015 target) for compatibility with Kindle's browser.
**Files:** `packages/client/src/main.ts`, `packages/client/src/progressStorage.ts`, `packages/client/src/i18n.ts`, `packages/client/src/fitGrid.ts`, `packages/client/src/hydratePlayPage.ts`, `packages/client/src/hydrateLibraryPage.ts`, `packages/client/src/hydrateEditorPage.ts`, `packages/client/src/imageQuantize.ts`, `packages/client/src/decodeImageFile.ts`, `packages/client/src/withTimeout.ts`, `packages/client/src/htmlFixture.ts`
**Exports:** `computeFitFontSizePx({naturalWidth, naturalHeight, availableWidth, availableHeight, baseFontSizePx, minScale, maxScale}): number` — pure function computing the single font-size (px) that scales an already `em`-sized grid to fit the available space: the smaller of the width/height fit ratios, a small safety margin, clamped to `[minScale, maxScale]` and rounded down (so a rounding error clips unused margin, never a real cell); falls back to the clamped base size when either the natural or the available size is zero/negative rather than dividing by zero; `main.ts` has no exports of its own — it is the shared entry point bundled for every generated page, importing `hydrateLibraryPage.ts`/`hydratePlayPage.ts`/`hydrateEditorPage.ts` purely for their self-invoking side effects. Each self-detects its own page shape by a marker unique to it and no-ops otherwise: `hydrateLibraryPage` by the embedded `#puzzles-data` script, `hydratePlayPage` by the embedded `#puzzle-data` script, `hydrateEditorPage` by a `data-role="editor-page"` marker. Import order no longer matters for this self-detection (unlike before the frozen-chrome refactor — see `.ux/decisions/001-frozen-chrome-blocking-reconciliation.md`): the editor page's grid canvas now renders a real `<table>` statically too, so a bare `<table>` stopped being a marker unique to the play page, which is exactly why `hydratePlayPage` switched to keying off `#puzzle-data` instead — a marker two page shapes could both satisfy caused a real double-hydration bug in this project before. Each module also wraps its own self-invoked `hydrate()` call in a try/catch (`if (typeof document !== "undefined") { try { hydrate(); } catch { … } }`): `main.ts`'s three imports are static `import` declarations, which can't themselves be wrapped in try/catch, so an uncaught error thrown while one module hydrates would otherwise halt the shared bundle's remaining synchronous top-level execution and silently stop the other two modules from ever being imported at all — each module now catches its own failure right at the self-invocation site instead, so the other two always get their turn regardless of what happens in the others (see backlog item 041 and `packages/client/src/main.test.ts`'s throw-simulation tests, which mock a dependency unique to one module to force a real, uncaught throw and assert the next module in import order still hydrates); `saveProgress(puzzleId, progress): boolean`, `loadProgress(puzzleId): PuzzleProgress | undefined` — persist/read a puzzle's progress to/from `localStorage`; `loadProgress` degrades silently (returns `undefined`) if storage is unavailable, throws, or holds corrupted JSON, but `saveProgress` reports a failed write back as `false` rather than swallowing it, so a caller can react (see `hydratePlayPage.ts`'s save-failure warning below and `.vibe/decisions/020-save-failure-warning-scoped-to-page-view.md`); `readLocaleCookie(): string | undefined` / `writeLocaleCookie(locale): void` — persist the player's language choice to a cookie named by `shared`'s `LOCALE_COOKIE_NAME` (`kindle-nonograms-locale`, also read by `site`'s pre-hydration `earlyLangScript.ts` — see `modules/site.md`), degrading silently if cookies are disabled or throw; `resolveLocale(cookieValue, navigatorLanguage): Locale` — pure function picking the effective locale (cookie, then browser language by primary subtag, then `DEFAULT_LOCALE`); `applyLocale(locale): void` — sets `document.lang`, retranslates every `[data-i18n]` element's text in place, and retranslates every `[data-i18n-aria]` element's `aria-label` in place, all with no reload and no DOM node created/removed/moved (so a currently focused element is never disturbed — see `.vibe/decisions/023-generic-aria-label-retranslation-attribute.md`); a translated `aria-label` containing a `{number}` token (the play page's numbered color swatches, and the editor's palette select/edit/remove controls) has that token substituted with the element's own 1-based `data-color-index`; a `{label}` token is substituted with the element's own current `textContent` (e.g. the library page's solved-puzzle link, whose visible name + dimensions are never themselves translated); a `{status}` token is substituted with the translated `library.solvedBadge` word, reused rather than duplicated so the linked spoken solved status can never drift from the visible badge's own text — each substitution is a no-op for any `[data-i18n-aria]` element with no such token or attribute (see `.vibe/decisions/029-swatch-aria-label-number-placeholder.md` and `.vibe/decisions/031-solved-link-aria-label-composes-badge-translation.md`); `extractBodyHtml(fullPageHtml): string` (`htmlFixture.ts`) — pure; pulls the `<body>` element's inner markup out of a full page HTML string, thrown if no `<body>` tag is found. Every `hydrate*.test.ts` fixture is built by calling `@kindle-nonograms/site`'s real `render*Page()` and feeding its output through this function, rather than a hand-retyped copy of the markup — the latter can silently drift out of sync with what the renderer actually produces (see `.ux/decisions/001-frozen-chrome-blocking-reconciliation.md`'s consequence about the drift risk this creates, and `packages/site/src/index.ts`, which re-exports the three `render*Page` functions specifically for this use); `contrastingTextColor` (WCAG black/white pick against a background hex) moved to `shared` — this package no longer defines its own copy; `hydrateEditorPage.ts` imports it from `@kindle-nonograms/shared` for its palette swatches, exactly as `site`'s `renderEditorPage.ts`/`renderPuzzlePage.ts` do for their own baked-in swatches, so both sides pick the identical checkmark color for the identical hex with no risk of drifting apart.

Every generated page's default chrome — the puzzle page's toolbar/win banner/storage warning, the library page's filters/pagination, the editor's palette/toolbar/canvas — is now baked into the static HTML by `site`'s `render*Page()` functions in its exact default shape (see `.ux/decisions/001-frozen-chrome-blocking-reconciliation.md`), not built from scratch by hydration on first load. `hydrate*.ts`'s job for each of these is now to *locate* that already-existing markup by its `data-role` attributes and attach behavior to it; the shared default values both sides must agree on (`PLAY_DEFAULT_MODE`, `PLAY_DEFAULT_ACTIVE_COLOR_INDEX`, `EDITOR_DEFAULT_WIDTH`/`HEIGHT`/`PALETTE`/`MODE`, `LIBRARY_PAGE_SIZE`) live in `shared`'s `uiDefaults.ts` so `site` and `client` can never silently disagree on what "default" means. A missing expected control is always a defensive no-op scoped to just that control, never a thrown error that could dead-end the rest of hydration.

`hydratePlayPage.hydrate(): void` — the interactive entry point for a generated puzzle page: resolves the locale (saved cookie, else the browser's detected language, else English) and calls `applyLocale` once — this page has no language switcher of its own, only the library and editor pages do (see `.vibe/backlog/done/026-language-switcher-and-contribution-footer.md` and `.vibe/decisions/022-editor-language-switcher-in-footer.md`), it just has to honor whatever choice was already made there, so all of the static markup's `data-i18n` text (including the toolbar/banner's default wording, present in the DOM from first paint) is retranslated immediately. It then locates the Fill/Cross mode toggle, Check button, and (for a multi-color puzzle) the color swatch buttons `renderPuzzlePage.ts` already baked in their default shape, and attaches click behavior plus `aria-pressed` syncing (`attachToolbar`) — it no longer builds any of this DOM itself. A color swatch's own active-state border-width toggle reads `shared`'s `BORDER_WIDTH.thick`/`.thin` tokens rather than a hardcoded literal, so it can never drift from the identical values `site`'s build-time render used for that same swatch's initial border-width (backlog item 052). It locates the win banner (`findBanner`, `[data-role="win-banner"]`) the same way; a missing banner only disables the win-confirmation feature, all other hydration (progress restore, the grid's click handling) still attaches. It restores saved progress onto the grid and wires one delegated click listener that toggles a tapped cell's mark, redraws only that cell, saves progress, and shows/hides the win banner via `isPuzzleSolved`. The Check button first runs `shared`'s `correctWrongCells` over the current progress, repaints only the cells it actually changed, and persists the result if anything changed, then reveals the banner with whichever message applies: the solved message if that correction left the puzzle solved, a distinct "some wrong cells were cleared" message (deliberately not phrased as "fixed" — the check only removes mistakes, it never fills in the correct answer for the player) if it cleared at least one wrong cell but the puzzle isn't finished, or the plain not-solved message if nothing was wrong to begin with — it never fills in a cell the player hasn't attempted, since `correctWrongCells` never treats an untouched cell as a mistake. Both this manual path and the automatic tap-triggered one route through a shared `setBannerMessage` helper (keyed directly by translation key rather than a solved/not-solved boolean, to accommodate the third "corrected" message) that also swaps the banner's `data-i18n` key to match, so a later language change re-translates whichever message is actually showing rather than reverting to a stale one. The banner carries `aria-live="polite"` so its message is announced to assistive tech whenever it changes; both paths always clear the banner's `hidden` attribute *before* writing its new text (never the other way round), since some assistive tech only announces an `aria-live` region's content change once the element is already unhidden — see backlog item 061. A filled cell gets a solid `background-color` matching its palette color and nothing drawn on top — a plain square; a crossed cell explicitly clears both background and text, so no fill color ever survives a filled→crossed transition. The color swatch buttons are likewise plain solid-color squares; only the active one carries a `✓` checkmark in `contrastingTextColor`'s pick, as the non-color cue for which color is selected — each swatch's numbered `aria-label` (baked by `renderPuzzlePage.ts`, see `modules/site.md`) is left untouched by this active/inactive toggle, since `attachToolbar` only ever sets `aria-pressed`/border width/the checkmark glyph, never the label. The grid-fit floor (`minScale`) is deliberately low enough to let a wide puzzle (e.g. 25 columns) still fit a narrow real screen rather than get clipped by `.grid-wrapper`'s overflow fail-safe — a puzzle silently missing cells/clues is strictly worse than one rendered smaller than the original, more conservative floor allowed; the actual rendered width isn't perfectly linear with the wrapper's `font-size` at very small scales, since border widths (`theme.ts`'s `BORDER_WIDTH`) are fixed px, not `em` — a real but minor source of drift the floor's own safety margin already has room for at realistic screen widths. `hydrate()` finishes by calling `computeFitFontSizePx` (via `fitGrid.ts`) to fit the grid to the available viewport space, applying the result as the grid wrapper's `font-size` — natural size is measured off the `<table>` itself rather than its wrapper `<div>`, since a `<div>` stretches to its container's width regardless of content while a `<table>` shrink-wraps to its own. It also sets the wrapper's `max-width`/`max-height` to the same measured available space: the wrapper's `overflow:hidden` (see `modules/site.md`) clips nothing on its own without a bounded box, so this pairing is what actually makes it a fail-safe rather than a no-op, even for a puzzle so large that the scale floor still isn't enough to make it fit. The fit re-runs on `resize`, whenever the win banner transitions from hidden to visible, and whenever the storage warning below is first shown (all three are the only events that can shrink the space left for the grid).

Also locates a fourth already-baked, hidden control: the one-time "progress can't be saved on this device" warning (`findStorageWarning`, `[data-role="storage-warning"]`, see backlog item 033 and `.vibe/decisions/020-save-failure-warning-scoped-to-page-view.md`). Every call that persists progress (a cell tap, a Check click) now routes `saveProgress`'s boolean result through a shared `reportSaveResult` closure: on the *first* failed save this page view it reveals the warning and re-fits the grid (the same hidden→visible re-fit trigger as the win banner); any further failed save this same page view is a no-op, tracked by a plain in-memory flag reset on every hydration (no `sessionStorage`/cookie — that decision explicitly rejected persisting the "already warned" state across reloads, see the ADR). The flag is set synchronously before anything else runs, so two failed saves in the same tick (e.g. a tap immediately followed by a Check click) can't both slip through and show/re-fit twice. A dismiss button inside the warning (`[data-role="storage-warning-dismiss"]`) hides it early on click without touching that flag, so dismissing doesn't bring the warning back on a later failure. The dismiss control follows the app's established icon-button convention: an `aria-hidden="true"` "×" glyph paired with a `.sr-only`-clipped translated label, rather than relying on `aria-label` alone.

A fifth already-baked, hidden control (`revealLoadError`, `[data-role="load-error"]`, see backlog item 040): when the embedded `#puzzle-data` script is present (this page's own self-detection marker already passed) but `readPuzzle()` still can't produce a valid `Puzzle` — missing/empty content, malformed JSON, or a shape `createPuzzle` rejects — `hydrate()` reveals this message instead of returning silently, so the player sees why the (now permanently inert) grid never became interactive, rather than a grid that looks tappable but does nothing. Its text is already translated by `applyStoredLocale`'s earlier full-page `[data-i18n]` pass, so revealing it only needs clearing `hidden`. This is a distinct failure from the self-detection no-op at the very top of `hydrate()` (an entirely different page shape with no `#puzzle-data` script at all, e.g. the editor page) — only a genuine puzzle page whose data turns out to be unreadable reaches this branch.

A sixth already-baked, hidden control (`findRestoreWarning`, `[data-role="restore-warning"]`, see backlog item 042): `readProgress` now reports whether a stored progress record existed but was discarded because its shape no longer matches the puzzle's current dimensions (e.g. the puzzle was resized since the player last played it), distinct from there being no stored record at all — only the former reveals this note, once, right when progress is restored (before `applyGridFit`'s own call at the end of `hydrate()`, so no extra re-fit trigger is needed the way the storage warning's later, action-triggered reveal requires). Unlike the storage warning, it has no dismiss button and no dedicated styling — it mirrors the plain, non-dismissible `load-error` treatment instead, since it reports a fact already true the instant the page loads rather than a live outcome of a user action, and it can never reappear this page view once shown (see `.vibe/decisions/026-restore-warning-follows-load-error-pattern.md`).

`hydrateLibraryPage.hydrate(): void` — the entry point for the generated home page: locates the FR/EN language switcher `site`'s shared `renderLanguageSwitcher()` (`renderLanguageSwitcher.ts`) already bakes into the page's `.page-footer` (English selected by default, since the locale itself isn't known at build time — the library and editor pages are the only ones with a switcher control, both built from this same shared markup so they can't diverge), sets its value to the resolved locale (saved cookie, else the browser's detected language, else English) and wires its `change` listener, then applies that locale (before checking whether the puzzle list is empty, so both the switcher and the translated empty-state message show up on an empty library too), reads every puzzle's full data embedded in the page. If the list is non-empty, it calls `setUpFiltersAndPagination`, which *locates* the size/color filter `<select>`s, the "no results" message, and the Previous/Next pagination controls `renderLibraryPage.ts`'s `renderFiltersAndPagination` already bakes into the static page in their default shape (both filters at "all", page 1) — it no longer builds any of this DOM itself. It wires them into one shared `render()` pass, triggered by either filter select's `change` event or a pagination button's `click`, that re-evaluates every row's `data-size-bucket`/`data-color-type` attributes (set server-side by `renderLibraryPage.ts`) with AND logic, keeps only the rows that also fall inside the current page's slice of that filtered result, and toggles `hidden` on every other row — rows are never removed or reordered, so the solved-badge/thumbnail reveal below keeps finding every row regardless of its filter/page state. This `render()` pass also runs once at setup, even though the static defaults already match its result — a safe, invisible no-op that only serves to initialize the closure's own `currentPage`/`totalPages` state. A filter change always resets the current page back to 1 before re-rendering; the Previous/Next buttons are disabled at the first/last page, and the whole pagination control stays hidden whenever the filtered result already fits on one page (`LIBRARY_PAGE_SIZE`, from `shared`'s `uiDefaults.ts`). Clicking Previous/Next also scrolls the puzzle `<ul>` back into view (guarded by try/catch, since `scrollIntoView` isn't implemented in every test/runtime environment) — without it, a player who just tapped Next stays parked next to what looks like stale content until they scroll up themselves, easy to miss on Kindle's slow e-ink refresh. A translated "no puzzles match" message (also already baked in, hidden) shows when the filter combination excludes every row. It then checks each puzzle's saved progress with `isPuzzleSolved`, and for each solved puzzle reveals the matching row's `.solved-badge` node, replaces its neutral "?" `.thumb` placeholder with a real preview built on the spot from `shared`'s `buildThumbnail` — one `.thumb-row`/`.thumb-cell` per downsampled cell, colored from the puzzle's own palette (blank for an empty cell), never pre-rendered server-side so an unsolved puzzle's picture never sits in the page's HTML at all (see `.vibe/decisions/012-solved-thumbnail-built-client-side-only.md`) — and sets the puzzle link's own `aria-label` (its visible text plus the translated solved status, tagged `data-i18n-aria` so a later language switch keeps it correct) since the sibling `.solved-badge` span alone never reaches the link's own accessible name (`.vibe/decisions/031-solved-link-aria-label-composes-badge-translation.md`, backlog item 050); an unsolved puzzle's link is left with no `aria-label` at all. A puzzle with no, incomplete, incorrect, or corrupted/wrong-shaped stored progress is treated as not solved and simply keeps its placeholder rather than marked or crashing.

`hydrateEditorPage.createEmptyCells(width, height)`/`resizeCells(cells, width, height)` — pure; build and resize a solution grid, preserving every cell still in bounds and never resurrecting content a previous shrink already dropped, `paintCell(cells, x, y, value)` — pure, immutable, out-of-range coordinates are a no-op returning the same reference, `addPaletteColor(palette, hex)`/`updatePaletteColor(palette, index, hex)` — pure; add or replace a palette color, `updatePaletteColor` ignoring a not-yet-valid typed hex (returns the same reference) rather than corrupting the palette mid-edit, `removePaletteColor(palette, cells, index, activeColorIndex)` — pure; drops a color, clears every cell that used it, shifts every cell (and the active color index) referencing a later color down by one to keep pointing at the same color in the shortened palette, and refuses to drop the last remaining color (a `Puzzle`'s palette needs at least one — see `createPuzzle`), `buildPuzzleCandidate(input)` — pure; trims the id/name fields (so a stray space typed into the filename/name field never ships) and hands the result to `createPuzzle`, the single validation path the editor's Export action relies on (see `.vibe/decisions/017-puzzle-editor-validates-on-export-only.md`), `triggerDownload(filename, content)` — saves `content` as a browser download via a throwaway Blob URL and a synthetic anchor click, the only way to hand a file to the contributor from a page with no server (see `.vibe/backlog/done/005-remove-express-server-package.md`), `hydrateEditorPage.hydrate(): void` — the interactive entry point for the puzzle editor page (see `modules/site.md`'s `renderEditorPage`): self-detects the page by its `data-role="editor-page"` marker, builds its in-memory `EditorState` starting from `shared`'s `EDITOR_DEFAULT_*` constants (the exact same values `renderEditorPage.ts` used to bake the page's default palette/toolbar/grid) plus a `locale` field resolved the same way as every other page, then calls `setUpLanguageSwitcher`: locates the footer switcher `renderEditorPage.ts` bakes in (same shared `renderLanguageSwitcher()` markup as the library page), sets its value to the resolved locale, wires its `change` event to persist the cookie and call `applyLocale`, and keeps `state.locale` updated so a later real re-render (resize, palette edit, import) keeps using the chosen language — `renderPalette`/`renderToolbar` and the `describeImportError`/`describeExportError` message-pickers all read `translate(state.locale, …)` rather than a hardcoded default, so a completed language switch can't be silently reverted by a subsequent edit. Each palette control's `aria-label` also carries a `data-i18n-aria` key (its accessible name isn't visible text, so `applyLocale`'s `data-i18n` mechanism alone can't retranslate it — see `.vibe/decisions/023-generic-aria-label-retranslation-attribute.md`); the select/edit/remove controls' translated labels each carry a `{number}` token, so `renderPalette` substitutes each element's own 1-based `data-color-index` into it (same mechanism as the play page's swatches, see `.vibe/decisions/029-swatch-aria-label-number-placeholder.md`), giving every color in the palette a distinct, position-numbered accessible name instead of an identical one shared across the whole palette. It then wires the width/height inputs (via `handleResize`, shared by both — an invalid entry, zero/negative/non-numeric, reports a fixed, translated `editor.error.invalidGridSize` message into the same error region before reverting the field to its previous valid value, instead of reverting silently; a valid entry clears the region the same way `describeImportError`/`describeExportError`'s own handlers already do — see `.vibe/backlog/done/043-explain-invalid-grid-size-input-in-the-editor.md`), name/filename fields, and Export/Import actions. On first load it does **not** call `render()` to build the palette editor, mode toggle, or grid canvas — those already exist in the page as real markup in their default shape (one black color, Paint mode, a 5×5 grid). Instead, three small, independently try/caught attach functions (`attachInitialPalette`, `attachInitialToolbar`, `attachInitialGridFit`) each locate that existing markup and wire listeners onto it via the exact same `wirePaletteRow`/`wireToolbarButtons` helpers `render()`'s own rebuild path uses, so the two never drift apart. Each runs in its own try/catch specifically so a failure attaching one (e.g. the palette) can never prevent the others (toolbar, grid fit) from attaching — see `.ux/decisions/001-frozen-chrome-blocking-reconciliation.md`. This matters here more than on the play/library pages because the editor's contributor persona uses a normal desktop browser with mouse *and* keyboard (see `.ux/product.md`): calling `render()` on load — which wipes and rebuilds the palette/toolbar/grid from scratch — would silently drop the focus of a keyboard user who had already started tabbing through the page to `<body>`. `render()` remains the full rebuild path for every actual state change afterward (resize, palette add/remove/edit, a cell paint, an image import) — unlike the play page's single-cell repaint, every one of these triggers a full re-render of the palette and grid; simple over clever, since this is a desktop authoring tool, not a Kindle e-ink page the "avoid a visible redraw" constraint applies to. The grid canvas reuses `fitGrid.ts`'s `computeFitFontSizePx` (same reasoning as `hydratePlayPage`'s own use of it) so a puzzle drafted much larger than any shipped one still fits the viewport, and a `beforeunload` listener guards against losing unsaved work by leaving the page. Export validates via `buildPuzzleCandidate` and, on failure, maps the thrown `PuzzleValidationError`'s `reason` (never its raw `message`, which stays plain-English/developer-facing for `discoverPuzzles.ts`'s build diagnostics) to a fixed, translated, contributor-facing message via `describeExportError` — only `emptyId`/`emptyName` (the two failures the editor's own fields can actually trigger) get a specific message, every other reason falls back to one generic message, same as any wholly unclassified error (see `.vibe/decisions/021-editor-errors-discriminated-by-reason.md`) — shown inline (prefixed with a fixed "⚠" glyph, styled with the `amber` accent rather than introducing a new color role) in a reserved, `aria-live="polite"` error region that never shifts surrounding layout, and on success calls `triggerDownload` with `<id>.json` and reveals a sibling reserved, `aria-live="polite"` confirmation region naming the downloaded file (prefixed with a fixed "✓" glyph, styled with the `teal` "completed" accent — the same role the play page's win banner and the library's solved badge already use — rather than a bordered banner, to match its plain-text error sibling right next to it; see `.vibe/decisions/028-export-confirmation-plain-text-teal.md`) — both regions are cleared at the start of every export attempt, so only one of the two ever holds text at once; also wires an "import image" action (see .vibe/backlog/done/030-image-import-for-the-puzzle-editor.md): reads the grid's *current* width/height at the moment the Import button is clicked (not whenever the file was picked, since those fields stay live-editable in between), asks for confirmation via the browser's native `confirm()` only when the grid already has painted content to lose (an empty grid applies the result directly, matching every other editor action's immediate-apply model), disables the file/palette-size/Import controls for the run's duration, decodes the picked file via `decodeImageFile.ts` raced against a fixed 15-second timeout (`withTimeout(promise, timeoutMs, onTimeout): Promise<T>` — a small, pure, directly unit-tested module kept separate from `decodeImageFile.ts` on purpose, so a stalled `onload`/`onerror` can no longer leave the import controls disabled forever without inheriting that file's real-browser-only verification boundary; the wrapped promise is only ever out-raced, never cancelled — a native `Promise` honors only its first `resolve`/`reject`, so a late settlement after the timeout already won is silently inert; see `.vibe/decisions/027-image-import-timeout-race-lives-outside-decode.md` and backlog item 044), feeds the result into `imageQuantize.ts`'s `buildImportedGrid` using the current width/height/palette-size/background-color inputs, and on success replaces the editor's palette/cells and switches into paint mode (this path does call `render()`, since it's a genuine state change, not first-load setup). `imageQuantize.ts` exposes `RGB`/`ImageLike` (types), `downsampleImage(image, targetWidth, targetHeight): RGB[][]` — pure block-averaging downsample (every target cell is the mean of the source-pixel rectangle it covers, so one noisy pixel can't dominate a cell the way nearest-neighbor would), `quantizeColors(pixels, paletteSize): {palette, indices}` — pure, dependency-free median-cut: repeatedly splits the largest still-splittable bucket along its widest color channel at a genuine value boundary (never inside a run of identically-colored pixels, which a raw index-median split can do, inflating the palette with duplicates) until there are `paletteSize` buckets or none left worth splitting, so fewer distinct colors than requested naturally yields a smaller palette, `buildImportedGrid(image, options): {palette, cells}` — ties both together, mapping every downsampled cell within a distance tolerance of a configurable background color to `null` (never spending palette budget on it) before quantizing only the remaining cells; degrades to an empty palette/grid rather than throwing for a zero-size target or an all-background image. `decodeImageFile.ts` exposes `decodeImageFile(file): Promise<ImageLike>` — the one DOM-only piece of this pipeline (a throwaway `<canvas>`: `Image()` load, `drawImage`, `getImageData`), kept in its own tiny module specifically so `hydrateEditorPage.ts`'s tests can mock it out, since jsdom (this project's test environment) doesn't implement real `<canvas>` pixel decoding — verified instead by driving a real browser, the same "DOM glue, not unit tested" boundary already drawn around `publish-preview-cli.ts`. Every rejection is an `ImageDecodeError` carrying a `reason` (`"unsupported"`: no 2D canvas context at all; `"unreadable"`: the picked file itself failed to load as an image; `"timeout"`: `hydrateEditorPage.ts`'s own `withTimeout` race won before the decode settled — `decodeImageFile.ts` itself never imposes a timeout; `"unknown"`: any other failure, most often a raw browser exception whose own wording is kept on the error for debugging but never shown to the contributor) — `hydrateEditorPage.ts`'s `describeImportError` maps it to a fixed, translated message the same way `describeExportError` does for `PuzzleValidationError` (see `.vibe/decisions/021-editor-errors-discriminated-by-reason.md`).
