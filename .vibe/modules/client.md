# Module: client
**Role:** Vanilla TypeScript frontend, built with Vite (es2015 target) for compatibility with Kindle's browser.
**Files:** `packages/client/src/main.ts`, `packages/client/src/progressStorage.ts`, `packages/client/src/contrastColor.ts`, `packages/client/src/i18n.ts`, `packages/client/src/fitGrid.ts`, `packages/client/src/hydratePlayPage.ts`, `packages/client/src/hydrateLibraryPage.ts`, `packages/client/src/hydrateEditorPage.ts`
**Exports:** `computeFitFontSizePx({naturalWidth, naturalHeight, availableWidth, availableHeight, baseFontSizePx, minScale, maxScale}): number` — pure function computing the single font-size (px) that scales an already `em`-sized grid to fit the available space: the smaller of the width/height fit ratios, a small safety margin, clamped to `[minScale, maxScale]` and rounded down (so a rounding error clips unused margin, never a real cell); falls back to the clamped base size when either the natural or the available size is zero/negative rather than dividing by zero; `main.ts` has no exports of its own — it is the shared entry point bundled for every generated page, importing `hydratePlayPage.ts`/`hydrateLibraryPage.ts`/`hydrateEditorPage.ts` purely for their self-invoking side effects (each self-detects its own page shape by a distinct marker and no-ops otherwise: `hydratePlayPage` by a `<table>`, `hydrateLibraryPage` by the embedded `#puzzles-data` script, `hydrateEditorPage` by a `data-role="editor-page"` marker) — `hydrateEditorPage.ts` is imported last, deliberately, since it's the only one of the three that can build a `<table>` of its own (the editor's grid canvas), and `hydratePlayPage`'s self-detection relies on no `<table>` existing yet at the moment it runs; `saveProgress(puzzleId, progress): void`, `loadProgress(puzzleId): PuzzleProgress | undefined` — persists a puzzle's progress to `localStorage`, degrading silently if storage is unavailable, throws, or holds corrupted JSON; `contrastingTextColor(backgroundHex): string` — picks black or white, whichever wins the WCAG contrast ratio against a given `#rrggbb` background, falling back to black for a malformed color instead of throwing; `readLocaleCookie(): string | undefined` / `writeLocaleCookie(locale): void` — persist the player's language choice to a `kindle-nonograms-locale` cookie, degrading silently if cookies are disabled or throw; `resolveLocale(cookieValue, navigatorLanguage): Locale` — pure function picking the effective locale (cookie, then browser language by primary subtag, then `DEFAULT_LOCALE`); `applyLocale(locale): void` — sets `document.lang` and retranslates every `[data-i18n]` element in place, no reload; `buildLanguageSwitcher(currentLocale, onChange): HTMLElement` — builds the FR/EN dropdown (a native `<select>`, deliberately not a custom control, for reliable behavior on Kindle's old WebKit) with a translated label, calling `onChange` on selection; `hydratePlayPage.hydrate(): void` — the interactive entry point for a generated puzzle page: resolves the locale (saved cookie, else the browser's detected language, else English) and calls `applyLocale` once — this page has no language switcher of its own, only the library page does (see `.vibe/backlog/done/026-language-switcher-and-contribution-footer.md`), it just has to honor whatever choice was already made there, so that static back-link's `data-i18n` markup is retranslated immediately on load. It then builds a Fill/Cross mode toggle, a "Check"/"Vérifier" button, and (once there is more than one palette color) a color swatch per entry, plus a win banner — all translated from the start and carrying `data-i18n` keys so a later language change retranslates them. The Fill button and any color swatches are appended together inside a shared `.fill-color-group` wrapper (always built, even for a single-color puzzle with no swatches, so the DOM shape doesn't branch), so the two visually read as one action — Cross and Check stay direct children of the toolbar, outside that group — and inserts the toolbar/banner into the static `.chrome-panel` wrapper when present (falling back to the old grid-adjacent insertion point otherwise), so they land inside its bordered/shadowed box alongside the heading and back-link rather than as bare page siblings (see `.vibe/decisions/014-puzzle-page-chrome-panel-wrapper.md`) — restores saved progress onto the grid, and wires one delegated click listener that toggles a tapped cell's mark, redraws only that cell, saves progress, and shows/hides the win banner via `isPuzzleSolved`. The Check button first runs `shared`'s `correctWrongCells` over the current progress, repaints only the cells it actually changed, and persists the result if anything changed, then reveals the banner with whichever message applies: the solved message if that correction left the puzzle solved, a distinct "some mistakes were fixed" message if it cleared at least one wrong cell but the puzzle isn't finished, or the plain not-solved message if nothing was wrong to begin with — it never fills in a cell the player hasn't attempted, since `correctWrongCells` never treats an untouched cell as a mistake. Both this manual path and the automatic tap-triggered one route through a shared `setBannerMessage` helper (now keyed directly by translation key rather than a solved/not-solved boolean, to accommodate the third "corrected" message) that also swaps the banner's `data-i18n` key to match, so a later language change re-translates whichever message is actually showing rather than reverting to a stale one. The banner carries `aria-live="polite"` so its message is announced to assistive tech whenever it changes. A filled cell gets a solid `background-color` matching its palette color and nothing drawn on top — a plain square; a crossed cell explicitly clears both background and text, so no fill color ever survives a filled→crossed transition. The color swatch buttons are likewise plain solid-color squares; only the active one carries a `✓` checkmark in `contrastingTextColor`'s pick, as the non-color cue for which color is selected. The grid-fit floor (`minScale`) is deliberately low enough to let a wide puzzle (e.g. 25 columns) still fit a narrow real screen rather than get clipped by `.grid-wrapper`'s overflow fail-safe — a puzzle silently missing cells/clues is strictly worse than one rendered smaller than the original, more conservative floor allowed; the actual rendered width isn't perfectly linear with the wrapper's `font-size` at very small scales, since border widths (`theme.ts`'s `BORDER_WIDTH`) are fixed px, not `em` — a real but minor source of drift the floor's own safety margin already has room for at realistic screen widths. `hydrate()` finishes by calling `computeFitFontSizePx` (via `fitGrid.ts`) to fit the grid to the available viewport space, applying the result as the grid wrapper's `font-size` — natural size is measured off the `<table>` itself rather than its wrapper `<div>`, since a `<div>` stretches to its container's width regardless of content while a `<table>` shrink-wraps to its own. It also sets the wrapper's `max-width`/`max-height` to the same measured available space: the wrapper's `overflow:hidden` (see `modules/site.md`) clips nothing on its own without a bounded box, so this pairing is what actually makes it a fail-safe rather than a no-op, even for a puzzle so large that the scale floor still isn't enough to make it fit. The fit re-runs on `resize` and whenever the win banner transitions from hidden to visible (the only banner change that can shrink the available space enough to matter); `hydrateLibraryPage.hydrate(): void` — the entry point for the generated home page: prepends the language switcher into the static `.page-footer` rendered by `renderLibraryPage.ts` (ahead of its `.page-footer-links` group — this is the only page that still gets a switcher control) and applies the resolved locale (before checking whether the puzzle list is empty, so both the switcher and the translated empty-state message show up on an empty library too), reads every puzzle's full data embedded in the page. If the list is non-empty, it also builds the size/color filter bar — two native `<select>`s (kept native, like the language switcher, for reliable Kindle touch/keyboard behavior), each option carrying its own `data-i18n` key so the same generic `applyLocale` walker retranslates them on a later language change with no extra wiring — inserted right before the puzzle `<ul>`, together with a Previous/Next pagination control inserted right after it, both skipped entirely on an empty library, since there's nothing to filter or page through (see `.vibe/backlog/done/027-pagination-for-the-puzzle-library.md`). A single shared `render()` pass, triggered by either filter select's `change` event or a pagination button's `click`, re-evaluates every row's `data-size-bucket`/`data-color-type` attributes (set server-side by `renderLibraryPage.ts`, see `modules/site.md`) with AND logic, keeps only the rows that also fall inside the current page's 25-row slice of that filtered result, and toggles `hidden` on every other row — rows are never removed or reordered, so the solved-badge/thumbnail reveal below keeps finding every row regardless of its filter/page state. A filter change always resets the current page back to 1 before re-rendering; the Previous/Next buttons are disabled at the first/last page (each click is a no-op past that bound) and the whole pagination control stays hidden whenever the filtered result already fits on one page. The page-position status text (`current / total`, e.g. "2 / 3") is rebuilt as a plain string on every render rather than marked `data-i18n`, so the generic `applyLocale` walker — which replaces a `data-i18n` element's entire text content — can never wipe its digits on a language switch; only its screen-reader-only label prefix and the Previous/Next button labels go through that mechanism. A translated "no puzzles match" message shows when the filter combination excludes every row, so a fully-filtered-out list never reads as a frozen page on Kindle's slow e-ink refresh. It then checks each puzzle's saved progress with `isPuzzleSolved`, and for each solved puzzle reveals the matching row's `.solved-badge` node and replaces its neutral "?" `.thumb` placeholder with a real preview built on the spot from `shared`'s `buildThumbnail` — one `.thumb-row`/`.thumb-cell` per downsampled cell, colored from the puzzle's own palette (blank for an empty cell), never pre-rendered server-side so an unsolved puzzle's picture never sits in the page's HTML at all (see `.vibe/decisions/012-solved-thumbnail-built-client-side-only.md`) — a puzzle with no, incomplete, incorrect, or corrupted/wrong-shaped stored progress is treated as not solved and simply keeps its placeholder rather than marked or crashing; `hydrateEditorPage.createEmptyCells(width, height)`/`resizeCells(cells, width, height)` — pure; build and resize a solution grid, preserving every cell still in bounds and never resurrecting content a previous shrink already dropped, `paintCell(cells, x, y, value)` — pure, immutable, out-of-range coordinates are a no-op returning the same reference, `addPaletteColor(palette, hex)`/`updatePaletteColor(palette, index, hex)` — pure; add or replace a palette color, `updatePaletteColor` ignoring a not-yet-valid typed hex (returns the same reference) rather than corrupting the palette mid-edit, `removePaletteColor(palette, cells, index, activeColorIndex)` — pure; drops a color, clears every cell that used it, shifts every cell (and the active color index) referencing a later color down by one to keep pointing at the same color in the shortened palette, and refuses to drop the last remaining color (a `Puzzle`'s palette needs at least one — see `createPuzzle`), `buildPuzzleCandidate(input)` — pure; trims the id/name fields (so a stray space typed into the filename/name field never ships) and hands the result to `createPuzzle`, the single validation path the editor's Export action relies on (see `.vibe/decisions/017-puzzle-editor-validates-on-export-only.md`), `triggerDownload(filename, content)` — saves `content` as a browser download via a throwaway Blob URL and a synthetic anchor click, the only way to hand a file to the contributor from a page with no server (see `.vibe/backlog/done/005-remove-express-server-package.md`), `hydrateEditorPage.hydrate(): void` — the interactive entry point for the puzzle editor page (see `modules/site.md`'s `renderEditorPage`): self-detects the page by its `data-role="editor-page"` marker, then wires the width/height inputs, the palette editor (one row per color: a `contrastingTextColor`-checkmarked select/activate swatch button, an `<input type="color">` to edit its hex, and a remove button disabled when only one color remains), a Paint/Erase mode toggle mirroring `hydratePlayPage`'s Fill/Cross pattern, and the grid canvas into the static shell's reserved containers. Unlike the play page's single-cell repaint, every edit (resize, palette add/remove/edit, a cell click) triggers a full re-render of the palette and grid — simple over clever, since this is a desktop authoring tool, not a Kindle e-ink page the "avoid a visible redraw" constraint applies to. The grid canvas reuses `fitGrid.ts`'s `computeFitFontSizePx` (same reasoning as `hydratePlayPage`'s own use of it) so a puzzle drafted much larger than any shipped one still fits the viewport, and a `beforeunload` listener guards against losing unsaved work by leaving the page. Export validates via `buildPuzzleCandidate`, surfaces `createPuzzle`'s thrown message inline (prefixed with a fixed "⚠" glyph, styled with the `amber` accent rather than introducing a new color role) in a reserved, `aria-live="polite"` error region that never shifts surrounding layout, and on success calls `triggerDownload` with `<id>.json`
