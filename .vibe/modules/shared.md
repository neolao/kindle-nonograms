# Module: shared
**Role:** Domain types and pure helpers shared across the project.
**Files:** `packages/shared/src/index.ts`, `packages/shared/src/puzzle.ts`, `packages/shared/src/clues.ts`, `packages/shared/src/progress.ts`, `packages/shared/src/adapters.ts`, `packages/shared/src/i18n.ts`, `packages/shared/src/thumbnail.ts`, `packages/shared/src/libraryFilters.ts`, `packages/shared/src/solvability.ts`, `packages/shared/src/duplicatePuzzles.ts`, `packages/shared/src/contrastColor.ts`, `packages/shared/src/uiDefaults.ts`
**Exports:** `Puzzle` (interface), `createPuzzle(input): Puzzle` — throws a `PuzzleValidationError` (a stable `reason` discriminant — `"emptyId"`, `"emptyName"`, `"invalidDimensions"`, `"emptyPalette"`, `"rowCountMismatch"`, `"columnCountMismatch"`, `"colorIndexOutOfRange"` — plus a plain-English `message` build-time diagnostics like `discoverPuzzles.ts` still depend on verbatim) for any structurally invalid input, so a UI caller (the puzzle editor) can pick its own translated, user-facing message per `reason` without parsing `message` text (see `.vibe/decisions/021-editor-errors-discriminated-by-reason.md`), `ClueRun` (interface), `PuzzleClues` (interface), `computeLineClues(line): ClueRun[]`, `computePuzzleClues(puzzle): PuzzleClues`, `PlayerCellMark` (type), `PuzzleProgress` (interface), `createEmptyProgressGrid(width, height): PlayerCellMark[][]`, `isPuzzleSolved(puzzle, progress): boolean`, `CorrectionResult` (interface: `cells`, `changed`), `correctWrongCells(puzzle, progress): CorrectionResult` — pure; returns a new grid with every cell that doesn't match the solution cleared back to untouched (`null`), sharing its per-cell "is this right" predicate with `isPuzzleSolved` so the two definitions of correctness can never drift apart; an untouched cell is never treated as wrong even where the solution requires a fill — only an actual player mark (a fill or a cross) that doesn't match counts as a mistake to clear, so this never completes a cell the player hasn't attempted, `BooleanGridExport` (interface), `fromBooleanGridExport(id, input): Puzzle`, `Locale` (type), `SUPPORTED_LOCALES`, `DEFAULT_LOCALE`, `LOCALE_COOKIE_NAME` (the `kindle-nonograms-locale` cookie name the player's chosen locale is persisted under — shared so `client`'s `readLocaleCookie`/`writeLocaleCookie` and `site`'s `earlyLangScript.ts`, which reads the same cookie from a pre-hydration inline script, can never drift onto different cookie names), `NATIVE_LOCALE_NAMES` (`Record<Locale, string>`, each locale's own display name for the language switcher), `TranslationKey` (type), `translate(locale, key): string`, `isSupportedLocale(value): value is Locale`, `buildThumbnail(puzzle, maxDimension): (number | null)[][]` — pure nearest-neighbor downsample of a puzzle's solution grid, capped so neither axis exceeds `maxDimension`; a single scale factor (from the longer axis) applies to both, so the result keeps the solution's true proportions; a puzzle already within the cap is returned unchanged, `SizeBucket` (type), `puzzleSizeBucket(puzzle): SizeBucket` — pure; groups a puzzle into `"small"`/`"medium"`/`"large"` by its total cell count (`width * height`), thresholds at 100 and 400 cells inclusive on the smaller bucket, `isMultiColorPuzzle(puzzle): boolean` — pure; `true` whenever `palette.length > 1`. Both back the library page's size/color filters (see `modules/site.md`, `modules/client.md`). `SolvabilityResult` (type: `{ ok: true } | { ok: false; reason: string }`), `checkSolvability(puzzle): SolvabilityResult` — pure "no guessing required" fairness check: a fixpoint line-solver repeatedly derives forced cells for every row/column from its clue via a dynamic-programming per-line feasibility check (not placement enumeration, so it stays fast on large grids), constrained by whatever earlier passes already forced, until nothing changes; `ok: true` only if every cell ends up determined and matches the puzzle's own solution (see `.vibe/decisions/016-line-solver-fairness-check.md`), `findDuplicatePuzzle(puzzle, existing): Puzzle | undefined` — pure; returns the first puzzle in `existing` whose `width`/`height`/`cells` exactly match `puzzle`'s, ignoring `id`/`name`/`palette`, `contrastingTextColor(backgroundHex): string` — picks black or white, whichever wins the WCAG relative-luminance contrast ratio against a given background, falling back to black for a malformed color instead of throwing; accepts strict 6-digit hex (`#rrggbb`), 3-digit shorthand (`#rgb`), and 8-digit hex with a trailing alpha byte (`#rrggbbaa`, alpha ignored — the fill always renders opaque as a swatch), normalizing each to 6-digit before computing luminance; moved here from `packages/client` so both `site` (baking a swatch's default checkmark color into static HTML) and `client` (rebuilding the same swatch after a palette edit) always pick the identical color for the identical hex — also used by `site`'s `renderPuzzlePage.ts` for a multi-color puzzle's clue-run swatches: the palette hex is now the run's *background* fill (like a filled grid cell) rather than its text, so both the text and the border color are this same contrast pick rather than the raw hex, keeping the border-style cue (`.vibe/decisions/003-clue-color-plus-pattern-cue.md`) visible against a same-hue fill instead of vanishing into it (`.vibe/decisions/033-clue-run-fill-reuses-contrastingtextcolor-border-follows-text.md`; superseded the earlier `readableRunColor` helper, now removed since the question it answered — is the palette hex legible as text on white — no longer applies), `LIBRARY_PAGE_SIZE`, `PLAY_DEFAULT_MODE`, `PLAY_DEFAULT_ACTIVE_COLOR_INDEX`, `EDITOR_DEFAULT_WIDTH`, `EDITOR_DEFAULT_HEIGHT`, `EDITOR_DEFAULT_PALETTE`, `EDITOR_DEFAULT_MODE`, `BORDER_WIDTH` (`uiDefaults.ts`) — plain constants naming every page's default UI state (puzzle rows per library page before pagination, the play page's starting paint tool/active color, the editor's starting grid size/palette/tool), plus `BORDER_WIDTH` (`{ thin: "1px", medium: "2px", thick: "3px" }`), the app's three border-width weights. Kept in one shared place specifically because `site`'s page renderers now bake each page's default chrome directly into its build-time HTML and `client`'s hydration scripts rebuild that identical default at runtime for any later state change (see `.ux/decisions/001-frozen-chrome-blocking-reconciliation.md`) — a constant duplicated on both sides instead would risk the two silently disagreeing on what "default" means. `BORDER_WIDTH` moved here from `packages/site/src/theme.ts` (which now only re-exports it) so `client`'s `hydratePlayPage.ts` can read the exact same values for its runtime border-width toggle instead of a duplicated literal (backlog item 052).
**Depends on:** (none)
