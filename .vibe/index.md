# Kindle Nonograms — Codebase index
> Generated by /vibe:sync on 2026-09-14 (incremental pass, 28). Re-run to update.

## Modules
- [`modules/shared.md`](modules/shared.md) — domain types and pure helpers shared across the project
- [`modules/client.md`](modules/client.md) — vanilla TypeScript frontend built with Vite
- [`modules/site.md`](modules/site.md) — static-site generator, starting with puzzle source loading

## Observed patterns
- The project no longer ships a runtime server — it is being rebuilt as a static site.
- Client code guards DOM access behind `typeof document !== "undefined"` so pure logic stays testable outside a browser.
- Domain types live in `shared` and are meant to be imported by both the client and, eventually, the static-site generator.
- Clues are never stored — they are always derived on demand from a puzzle's solution grid.
- Browser-API-dependent client tests opt into a per-file `// @vitest-environment jsdom` pragma rather than switching the whole suite's default environment.
- Puzzle source files are auto-detected by shape (native vs. reMarkable export) rather than by a format tag, and a source file's id always comes from its filename, never from content.
- Rendered puzzle pages inline all their own CSS in a `<style>` block (no external stylesheet exists yet) and never encode information by color alone, since Kindle's e-ink screens are often grayscale.
- Client-side updates to the puzzle grid touch only the single cell that changed, never rebuilding the grid, to avoid a visible redraw on Kindle's slow e-ink refresh.
- Generated pages keep their visible markup solution-blind but embed the full puzzle data as JSON regardless, since the site has no backend to hide solutions behind anyway.
- Every generated page loads the same client bundle; each hydration script self-detects whether its expected markup is present and no-ops otherwise, rather than the build shipping a separate bundle per page shape. Each page shape has its own distinct, unambiguous marker for this (the embedded `#puzzle-data` script for the puzzle page, the embedded `#puzzles-data` script for the library page, a `data-role="editor-page"` marker for the editor) — a marker two page shapes could both satisfy (e.g. just "an `<h1>` exists", or, once the editor's own canvas started rendering a real `<table>` too, a bare `<table>`) caused a real double-hydration bug once tried, which is exactly why the puzzle page's own marker was moved off `<table>` and onto its embedded JSON script instead.
- Filled grid cells and color-swatch buttons render as plain solid-color squares — no shape glyph is drawn on top, only the active swatch carries a checkmark, whose color is picked by actual WCAG contrast ratio against both black and white (not a fixed luminance threshold) so it stays legible against any arbitrary palette color.
- Any UI text meant to be retranslatable client-side carries a `data-i18n` key holding its translation key; a single generic `applyLocale(locale)` call re-walks every `[data-i18n]` element in the page and swaps its text in place, whether the element came from server-rendered HTML or was built later in client JS.
- Visual design tokens (colors, spacing, border widths, font stack) are plain TS constants interpolated into literal CSS strings at build time, never CSS custom properties (`var()` support on Kindle's old WebKit is uncertain).
- A block element with `overflow:hidden` clips nothing unless it also has an explicit bounded size — `max-width`/`max-height` set from a real measurement is what turns that CSS declaration into an actual fail-safe.
- A `<table>`'s natural size is measured directly off the `<table>`, never off a wrapping `<div>` around it — a `<div>` stretches to its container's width by default regardless of content, which would misreport a small puzzle's true size.
- Chrome spacing (margins/padding/borders on headings, toolbars, banners, the header row) is always applied to individual elements, never to `body` or the puzzle page's `.grid-wrapper` — the grid-fit measurement reads the raw viewport size, so any spacing added to an ancestor of the wrapper would silently make it overflow its computed cap.
- Every generated page's `<head>` opens with a tiny non-module, blocking inline `<script>` (`site`'s `earlyLangScript.ts`) — placed right after `<meta charset>`, ahead of everything else — so a client-only value with no per-request server render to resolve it (here, the visitor's saved locale cookie) can still affect the page before the browser paints or the deferred module bundle runs; a classic inline script runs synchronously in place, unlike a `<script type="module">`, which is always deferred past the full parse.
- The site deliberately uses a three-accent color system (superseding an earlier single-muted-accent rule — see `.vibe/decisions/013-three-accent-cabinet-reskin.md`): each accent has one fixed, reused role across both pages (navigating away/active toggle, the primary in-puzzle action, "completed" shared by the win banner and the library's solved stamp so the two visibly connect) so the palette reads as a deliberate system, plus separate decorative-only cycling on the marquee dot row that carries no meaning (the library card's top stripe used to cycle the same way but now reflects the puzzle's own palette instead — see `.vibe/decisions/015-library-card-stripe-reflects-palette.md`). The puzzle grid's own rendering (clue borders, cell/palette colors) is never touched by these accents, so it stays the calmest, most legible element on the page regardless of how bold the chrome around it gets.
- A second, monospace font layer is applied only to headings/buttons/badges/section labels, never body copy or fine print — at Kindle's small rendering sizes monospace looks cramped for anything longer than a short label.
- A static link meant to work before/without JavaScript is rendered server-side, never built by a hydration script — a hydration-built control is invisible until hydration finishes and unusable if it never runs at all.
- A derived visual (a rendered preview, not the raw embedded solution JSON) that would spoil a puzzle before it's solved is built client-side only, on confirmed proof of having solved it — server-rendering it hidden-until-revealed still leaves it sitting in the page's HTML source, which is a real difference from the already-accepted "full solution is embedded as JSON anyway" baseline.
- Fixed-size decorative UI (a thumbnail box) keeps an identical footprint across its placeholder and revealed states, swapping only inner content, so a state change never shifts surrounding layout.
- A "pressed in" button look (an offset shadow that flattens) is applied as a discrete style swap on `:active` and on `aria-pressed="true"` alike — never a `transition` — so a held-down button and a persistently active toggle read the same way without violating the no-animation e-ink constraint.
- Corner radius is a single shared token applied everywhere in the visual system, including elements the grid-fit calculation measures (the puzzle grid's own frame) — safe because border-radius is purely decorative and never affects box size or layout measurement, unlike padding/margin/border-width.
- A control whose border-width changes on state (a pressed/active button) keeps its outer box size fixed two different ways depending on how that control is sized: `box-sizing:border-box` alone is enough for a control pinned to a fixed floor (e.g. `MIN_TAP_TARGET_PX` on a color swatch, whose own content is always smaller than that floor), but a control sized by its own auto-width content (a text button like Fill/Cross/Check) needs its padding shrunk by exactly the border-width increase on every edge too — `box-sizing` only reinterprets an *explicit* width/height, and an auto-width box has none (see backlog item 052).
- Two chrome elements that need their own separate bordered boxes (the puzzle page's control panel and its grid frame) are kept as sibling elements, never one nested inside the other — nesting would force a shared padded container, which is exactly what the grid-fit measurement can't tolerate.
- Chrome height on the puzzle page specifically is treated as a real, measured budget, not an aesthetic afterthought — a decorative element kept on the library page (the dot row) is dropped on the puzzle page alone, since headless-browser measurement showed the combined header chrome eating over a third of a small Kindle-sized viewport before the grid even started. Two rows that can share one line (a heading and its adjacent controls) are merged rather than stacked, with `flex:1;min-width:0` plus `text-overflow:ellipsis` on the heading so a long title truncates instead of colliding with or pushing those controls — `min-width:0` specifically because a flex item's default `min-width:auto` otherwise prevents it from ever shrinking below its content's natural width, silently defeating the ellipsis. The same `min-width:0` + single-line-ellipsis pattern is reused for the library page's row link, so a long/UUID-fallback puzzle name truncates instead of wrapping and inflating just that one card's height relative to its neighbors.
- An icon-only control never relies on `aria-label` alone for its accessible name: the icon glyph sits in its own `aria-hidden="true"` element, paired with a `.sr-only`-clipped span carrying the full translated label — visually hidden via the standard clip technique (never `display:none`/`visibility:hidden`, which would also strip it from the accessibility tree), so the same generic `[data-i18n]`-walking translation mechanism keeps working unchanged on it.
- A plain Unicode glyph used for a functional icon is deliberately picked from a widely-supported block (Dingbats/Arrows) already proven safe elsewhere in the app, never a rarer symbol block or a color emoji — old e-ink WebKit's font coverage for anything outside the most common ranges is a real, unverifiable-in-advance risk (a silent blank/tofu box), so an imperfect-but-safe metaphor beats a perfect-but-risky one.
- Buttons that represent one combined action (e.g. choosing a fill color as part of filling) are wrapped in their own small bordered sub-container nested inside the toolbar, styled with softer tokens (`panelEdge`/`paper`) than the app's main panel treatment (`border`/`panel`) — a deliberately lighter visual weight so a nested grouping cue never competes with the page's actual panels.
- The grid-fit shrink floor is a concrete minimum legible font size (10px of the 16px base), not an arbitrary ratio — a puzzle that would need an even smaller scale to fit a narrow real screen now stays at that floor and relies on `.grid-wrapper`'s `overflow:auto` to scroll to the rest of the grid, rather than trading legibility for a scale that avoids a scrollbar (see `.vibe/decisions/032-grid-legibility-floor-scrolls-instead-of-clipping.md`). Border widths stay fixed px (not `em`) even though the rest of the grid scales by `font-size`, so real rendered width at very small scales drifts slightly from the pure linear prediction — a minor effect the floor's own safety margin already tolerates at realistic screen widths.
- A border meant to stay visible against its own filled background is colored to match the contrast-computed text color, not the fill's own hex — a same-hue border optically vanishes into its own fill, silently erasing whatever non-color cue it was meant to carry (see `.vibe/decisions/033-clue-run-fill-reuses-contrastingtextcolor-border-follows-text.md`).
- A puzzle's palette hex values, when interpolated into a page's shared `<style>` block, are validated against a strict hex-color pattern first, falling back to black for anything that doesn't match — required wherever one page's stylesheet folds together data from more than one puzzle (e.g. every card on the library page), since an unvalidated value there is a CSS-injection surface in a way a single curated puzzle's own page isn't.
- Client-side visibility toggling (a solved badge, a filtered-out library row) always sets the `hidden` boolean property on the existing element rather than removing or reappending it — every other id-based hydration lookup keeps finding the element regardless of its current visibility state.
- A row's own filterable/derivable properties are tagged as a plain `data-*` attribute for filtering logic to read, computed wherever the underlying fact is actually knowable: color type is static per-puzzle content, so `site` bakes it server-side (`data-color-type`) at build time; solve status depends on the player's own saved progress, so `client` computes and tags it (`data-status`) once during hydration, before the first filter pass — neither is ever recomputed in the browser from the embedded puzzle JSON on every filter change (see backlog item 072, `.vibe/decisions/044-status-filter-computed-client-side.md`).
- Two or more independent toggle-button groups needing the same "tap to select, tap the active one again to clear back to 'all'" interaction share one small generic helper (taking a list of `{value, button}` entries and an `onChange` callback) rather than each group hand-rolling its own near-identical click wiring — the color filter (2 buttons) and the status filter (3 buttons) are the first two instances (backlog item 072).
- A player preference bundling more than one field into a single cookie (e.g. the library's color/status/sort selection) validates and defaults each field independently on read, the same tolerant spirit as the single-field locale cookie's `resolveLocale` — an old-shaped or hand-edited cookie loses only the one field that fails to parse, never the whole saved preference.
- Puzzle content validation (fairness/solvability, duplicate detection) lives in `shared` as pure functions and is wired into `site`'s loading path, never into `createPuzzle` itself — structural validation (`createPuzzle`) and content-quality validation are kept as separate, independently callable checks.
- An expensive-looking per-line check (e.g. a nonogram line solver) is implemented as a dynamic-programming feasibility oracle over the line, never by enumerating and materializing every possible placement — the latter blew the heap on a real 45×45 puzzle during this project's own development.
- A contributor-facing authoring tool (the puzzle editor) deliberately does not follow the play page's "repaint only the changed cell" discipline — that constraint exists for Kindle's slow e-ink refresh, which doesn't apply to a page run in a normal desktop browser, so the editor fully re-renders its palette and grid after every edit instead, simple over clever.
- A page whose own interactive script can build a `<table>` dynamically (the puzzle editor's grid canvas) is imported last in the shared client entry point, after every other hydration script that self-detects by checking for an existing `<table>` — importing it earlier would let its freshly-built table falsely satisfy that other check before the dynamically-built one even exists at parse time.
- A privileged GitHub Actions workflow triggered by `workflow_run` (needed whenever a low-privilege `pull_request` job must hand off to something with write access) never trusts a PR number carried inside an artifact the low-privilege job produced without independently cross-checking it against GitHub's own commit→PR association API first — the artifact is PR-controlled content, so its declared identity has to be confirmed, not assumed.
- `git add -A -- <pathspec>` hard-errors when the pathspec matches nothing left to add (an empty directory, or a deletion an earlier call in the same run already fully staged) — this is treated as "nothing new to stage" via a try/catch around the `add` call itself, not a `git status` pre-check, since status can still report something "pending" in a state `add` has genuinely nothing left to do for.
- A binary encoder needing only a narrow, well-defined format (e.g. a PNG with a single filter type and no interlacing) is written directly against Node's own built-ins (`node:zlib`'s `deflateSync`/`crc32`) rather than pulling in an image/canvas library, when the full format's generality isn't needed.
- The site's first external (leaves-the-app) link states that fact in its visible wording itself (naming the destination, e.g. "on GitHub") plus a trailing "↗" glyph — never color alone, and never only `target="_blank"` with no visible cue, since the whole point is a tap-only e-ink visitor knowing before tapping that it leaves the Kindle browser. The glyph itself is `aria-hidden`, so the same fact is repeated as translated `.sr-only` text inside the same link (after the glyph) for assistive tech — an icon-only visual cue never carries the whole story unless it also has a text equivalent in the accessibility tree.
- Every adaptive chrome layout in the site (header row, filter bar, and now the library footer) stacks on a narrow screen via a plain `display:flex;flex-wrap:wrap` container, never an `@media` breakpoint — the project has never introduced one, on the reasoning that flex-wrap alone, verified by rendering at a real narrow width, already produces an acceptable stacked layout.
- A CSS class rule that sets its own `display` value on an element also toggled via the `hidden` attribute is scoped `.foo:not([hidden])`, never plain `.foo` — a class selector and the `[hidden]` attribute selector share the same specificity, so a plain `.foo{display:...}` declared later in the stylesheet silently wins over `[hidden]{display:none;}` regardless of the attribute's actual value, defeating the hide. Caught by driving the built site in a real browser (jsdom-based tests only assert the `hidden` DOM property, never the resulting computed style, so they can't catch this).
- When `site`'s `build.ts` calls Vite's programmatic `build()` with a `configFile` from `packages/client`, options that default relative to `root` (e.g. `publicDir`) still resolve against `process.cwd()` — not the config file's own directory — since `root` itself isn't overridden. Any option meant to reach into `packages/client` from that call has to be passed explicitly with an absolute path; relying on Vite's own default silently no-ops instead of erroring.
- An editor action that outright replaces a whole chunk of state (not a merge, not a single field) asks for confirmation via the browser's native `confirm()` only when there's actual content at risk of being lost — an already-empty target applies the result directly, matching every other editor action's own immediate-apply-no-undo model, so a genuinely destructive action gets a guard the rest of the editor doesn't need without over-prompting when nothing would actually be lost.
- A control that reads another live-editable field's value as part of its own action (e.g. the image importer reading the grid's width/height) always reads it at the moment the action actually runs, never at an earlier "setup" moment (e.g. when a file was picked) — those fields stay editable in between, so reading early can silently use a stale value.
- DOM-only glue that a project's test environment can't meaningfully exercise (e.g. real `<canvas>`/`Image()` pixel decoding — jsdom doesn't implement it) is kept in its own small, thin module, isolated from the pure/testable logic it feeds, and documented as verified by driving a real browser instead of by unit tests — the same boundary already drawn around `publish-preview-cli.ts`, now reused for `decodeImageFile.ts`.
- A privileged script that both reads a live external list (e.g. currently open PRs) and reads/mutates a stored state it's about to diff against that list (e.g. checking out a branch to inspect it) always does the live read *first* — any change that lands in the gap between the two reads then belongs, by construction, to whichever side already reflects it, so the gap can only ever make the script more conservative, never cause it to act on something that changed underneath it. Reordering these two reads would reopen a real race window rather than just being a style choice.
- Every page's default chrome (the puzzle page's toolbar/win banner/storage warning, the library page's filters/pagination, the editor's palette/toolbar/canvas) is now baked directly into static HTML in its exact default shape by `site`'s `render*Page()` functions, rather than built from scratch by client hydration on first load; hydration only locates that markup by its `data-role` attributes and attaches behavior. A handful of controls whose true state is only known client-side (the win banner, solved badges) are still corrected by a synchronous, blocking check before the page is perceived as painted, rather than through a visible loading state — any visible post-paint transition (a dimmed→active flip, a wrong→right flash) works directly against the e-ink no-animation constraint (see `.ux/decisions/001-frozen-chrome-blocking-reconciliation.md`).
- The default UI state values a page's static rendering and its hydration-time rebuild must agree on (the play page's starting mode/active color, the editor's starting grid size/palette/tool, puzzles shown per library page before pagination) live in one shared module (`shared`'s `uiDefaults.ts`) rather than being declared independently on each side, so the two can never silently drift into disagreeing about what "default" means. The same module also hosts a plain visual token (`BORDER_WIDTH`) for the identical reason, whenever `client`'s runtime needs the exact value `site`'s build-time render already used for the same property (backlog item 052) — `site`'s own `theme.ts` only re-exports it, since `client` can't reach a `site`-only module.
- A hydration test's DOM fixture is built by calling the real `site` package's `render*Page()` function and extracting its `<body>` markup (`client`'s `htmlFixture.ts`), never a hand-retyped copy of that markup — the latter can silently drift out of sync with what the renderer actually emits once the two evolve independently.
- A WCAG-contrast color-pick helper needed identically by both a build-time static renderer and a runtime hydration rebuild (`contrastingTextColor`) lives in `shared`, not in whichever side happened to need it first — moved there from `client` once `site` also needed to bake the same computed swatch color into static HTML, so the two can never pick different colors for the same input hex.
- A function that used to degrade a failure silently (returning `void`) switches to reporting it back as a boolean once a caller actually needs to react to that specific failure — `saveProgress` now returns `false` on a failed write so the play page can show a one-time warning, while every other storage helper in the same client (`loadProgress`, the locale cookie read/write) still swallows silently, since nothing yet consumes their failure signal.
- A one-time, dismissible, per-page-view warning (shown once even if the underlying failure recurs) is tracked by a plain in-memory boolean, set synchronously on first occurrence before anything else runs, so two occurrences in the same tick can't both slip through; dismissing it early never resets that flag, so a later recurrence doesn't bring the warning back. No new storage primitive is introduced for a scope this narrow — the in-memory flag already matches every other piece of transient play state (see `.vibe/decisions/020-save-failure-warning-scoped-to-page-view.md`).
- An `aria-live` region's `hidden` attribute is always cleared before its announced text is (re)written, never after — some assistive tech only announces a live region's content change once the element is already unhidden, so setting the text first risks a silently missed announcement (see the win banner's two reveal paths in `hydratePlayPage.ts`).
- An error a UI must show translated/user-facing text for, but whose throwing function also has other, developer-facing callers (build-time diagnostics, logs) that already depend on its exact `message` wording, carries a separate stable `reason` discriminant instead of changing `message` — the UI switches on `reason` to pick its own translated string, `message` stays untouched, and anything the UI doesn't recognize (including a raw, unclassified browser exception) falls back to one fixed generic message rather than ever displaying the original text (see `.vibe/decisions/021-editor-errors-discriminated-by-reason.md`).

- A translated `aria-label` (an accessible name that isn't visible text, so the existing `[data-i18n]`/`textContent`-swap mechanism can't reach it) is retranslated via a parallel `data-i18n-aria` attribute, handled generically inside the same shared `applyLocale()` call rather than a page-specific rebuild — used first by the puzzle editor's palette buttons.
- A translated `aria-label` that also needs a per-element number (the play page's color swatches, "Color 2"; the editor's palette select/edit/remove controls, "Select color 2") carries a literal `{number}` token in its translation string, substituted generically inside the same `applyLocale()` call from the element's own `data-color-index` — a no-op for any other `data-i18n-aria` element, so this stays one shared mechanism rather than a second, page-specific retranslation path.
- Markup shared verbatim by more than one generated page (e.g. the FR/EN language switcher, now used by both the library and editor pages) lives in its own small `site` module, imported by each page's renderer, rather than being copy-pasted or kept private to whichever page had it first.
- A static ES `import` declaration can't itself be wrapped in try/catch, so isolating one statically-imported module's failure from the next one imported after it (the three page-hydration modules `main.ts` loads) is done by having each module catch its own uncaught error right at its self-invocation site, not by the importer — see backlog item 041.
- A one-time hidden-by-default note revealed by hydration follows one of two established shapes depending on what it reports, never a blend of the two: a fact already true the instant the page loads (e.g. the puzzle data is unreadable, or saved progress no longer fits the puzzle's dimensions) gets the plain, undecorated, non-dismissible `load-error` treatment; a live outcome of something the player just did (e.g. a save failed) gets the amber-bordered, dismiss-button `storage-warning` treatment instead — see `.vibe/decisions/026-restore-warning-follows-load-error-pattern.md`.
- An async operation whose only failure mode is "never settles" (a browser API call with no built-in timeout, e.g. the editor's `<img>`-based image decode) is raced against a fixed timeout by a small, generic, pure `withTimeout()` helper living outside the operation's own module, rather than the timeout being built into that module directly — kept separate specifically so the timeout race itself gets real, deterministic unit-test coverage (fake timers) instead of inheriting the real-browser-only verification boundary of DOM-only glue code it wraps. The wrapped operation is only ever out-raced, never cancelled; a late settlement after the timeout already won is silently inert by construction (a native `Promise` only ever honors its first `resolve`/`reject`) — see `.vibe/decisions/027-image-import-timeout-race-lives-outside-decode.md`.
- The `{number}` aria-label placeholder mechanism generalizes to two more tokens rather than growing a second, parallel substitution path: `{label}` (the element's own current, never-translated `textContent`) and `{status}` (another translation key's own current value, reused rather than duplicated so two spoken/visible texts describing the same concept can't drift apart) — first used by the library page's solved-puzzle link, whose accessible name must both keep its own visible text (name + dimensions) and append the same translated "solved" word the sibling visible badge already shows, so the solved status a screen reader hears matches what a sighted player sees — see `.vibe/decisions/031-solved-link-aria-label-composes-badge-translation.md`.
- Vertical spacing between more than one instance of the same repeated stacked element (a multi-color column clue's stacked run divs) is added via a CSS adjacent-sibling selector (`.foo+.foo{margin-top:...}`) on a class applied only when there is more than one instance to begin with, rather than an inline style computed per index — the selector alone already exempts a lone instance from ever getting the margin, so the "only between siblings" and "only when multi-color" conditions each live in exactly one place instead of being re-checked in both the markup and the CSS.
- Each panel of the puzzle editor owns its own inline status/error element, placed right next to its own controls, rather than several panels sharing one distant feedback node — the editor's Import section and its Name-and-export panel each clear-and-repopulate only their own element, deliberately never cross-clearing the other's, so a leftover message in one panel survives an unrelated action in another (see `.vibe/backlog/done/055-move-import-feedback-next-to-the-import-controls.md`).
- A keyboard-navigable grid of many identically-shaped focusable cells (the editor's paint canvas) uses a roving tabindex (one cell `tabindex="0"`, the rest `"-1"`) rather than making every cell its own Tab stop, with exactly one delegated `focusin` listener on the container — never one per interaction type — as the single source of truth for which cell is current, so a mouse click, a Tab-in, and an arrow-key move can never disagree. When the grid is fully torn down and rebuilt on unrelated state changes (resize, palette edit), the remembered current-cell coordinates are clamped to the new dimensions and reapplied, restoring live focus only if it was actually inside the grid at rebuild time — see `.vibe/decisions/034-editor-canvas-roving-tabindex-with-clamped-focus-preservation.md`.
- A standalone mode-toggle button is dropped once a more specific control already implies the same mode switch (tapping a palette color swatch also selects paint/fill mode) — but only where that other control is guaranteed to exist; where it can legitimately be absent (a single-color puzzle's play page renders no color swatches at all), the explicit toggle button stays, and the code that would otherwise require it is relaxed to make just that one control optional rather than mandatory (see backlog items 065, 070).
- Two independent toggle buttons standing in for a `<select>`'s three-way choice (all / one value / the other value) treat "neither pressed" as the missing third state — tapping whichever button is already active returns to it, rather than a `<select>`'s always-has-some-value model (see backlog item 067).
- A sort feature reorders the real DOM elements themselves (`Element.appendChild` on an already-attached node relocates it in place) rather than only toggling visibility/position via CSS or a separate index — existing logic that already just reads "whatever order the elements are currently in" (a filter/pagination pass) then needs no change at all to also respect the new order. The pre-sort order is snapshotted once at setup so toggling the sort back off can restore it exactly (see backlog item 068).
- A comparator that must keep "no value for this field" items separate from valued ones uses a stable partition (filter into two arrays in original order, concatenate) rather than a numeric comparator coercing the missing value to a sentinel (`0`/`-Infinity`) — a sentinel would also silently reorder the no-value group among itself, which a partition never does (see backlog item 068).
- A downsampling/preview-building function that used to take the owning domain object directly is widened to take just the plain data it actually operates on (a cell grid) once a second caller needs to feed it a different-but-same-shaped source (a player's own in-progress marks, not the puzzle's canonical solution) — avoids a second, near-duplicate implementation for the new case (see `.vibe/decisions/036-partial-progress-thumbnail-extends-buildthumbnail.md`).
- A derived preview built from partial/in-progress player data is suppressed — falling back to the same placeholder used for "nothing happened yet" — whenever it would otherwise be visually indistinguishable from that empty state (e.g. progress consisting only of exclusion marks, nothing actually painted); see backlog item 071.
- Two tabs open on the same puzzle stay in sync via the browser's native `storage` event (fires in every other same-origin tab on a `localStorage` write, never in the tab that made it) rather than polling or `BroadcastChannel` (unsupported on Kindle's old WebKit) — the resync repaints every cell by mutating existing DOM nodes in place, never rebuilding them, and is deliberately scoped to only the live state (grid, win banner); one-time load-time/action-scoped notes (the storage/restore warnings) keep their own existing lifecycle untouched by it — see `.vibe/decisions/037-cross-tab-progress-sync-scoped-to-grid-and-banner.md`.
- A decorative preview that must show the full accuracy of its source data, not an approximation of it (the library page's revealed puzzle thumbnail), scales down by shrinking each unit's on-screen size, never by merging/point-sampling fewer units than the source actually has — the fixed-footprint box stays fixed, but a single cell size computed as (box size) ÷ (source's longer dimension) is applied per instance instead of a single shared constant, and that size is left as an exact, unrounded CSS length so it can't collapse to invisible or overflow its box. A downsampling helper written for a different consumer with a different reason to shrink data (`shared`'s `buildThumbnail`, still used by `site`'s PR-preview PNG renderer to bound a bot-posted image's file size) is not reused here once its own approximation becomes the defect being fixed — see `.vibe/decisions/038-thumbnail-drops-downsampling-renders-every-cell.md`.
- A user-adjustable dimension with no natural upper bound (the editor's grid width/height) gets a hard cap enforced twice, deliberately not once: the HTML `max` attribute as a hint (a browser doesn't stop an out-of-range `change` event from firing) and a plain numeric range check in the actual handler as the real authority — the same relationship the image-import palette-size field already has with its own `max="16"`. A rebuild whose cost scales with that dimension (rebuilding the grid `<table>`) reuses an already-established busy-state convention (disable the relevant controls, show a plain status message, yield one frame, do the work, clear and re-enable) only once a cell-count threshold is crossed, rather than unconditionally — keeping every already-instant smaller case exactly as instant as before instead of adding a uniform yield that would flash a busy message on trivial input. See `.vibe/decisions/039-editor-resize-cap-and-cell-count-async-threshold.md`.
- A shared viewport-fit helper (`fitGrid.ts`'s `computeFitFontSizePx`) takes its height constraint as optional rather than growing a second, near-duplicate width-only function: a fixed no-scroll page (the play page's Kindle chrome) passes both width and height so the grid can never grow taller than the viewport, while a normally-scrolling desktop page (the puzzle editor) omits height entirely so a short browser window can't shrink the canvas just because height is scarce — the page grows and scrolls instead. Omitting the height argument, not passing a synthetic huge value, is what makes "no height constraint" explicit at the call site rather than an implicit trick relying on how the ratio math happens to behave at the extreme.
- A build-time-only validation function that reports only the first problem it finds (`shared`'s `checkSolvability`, which throws/rejects a whole submission) grows a second, total sibling (`diagnoseSolvability`) rather than changing its own contract, once a live UI (the editor's on-demand "check solvability" button) needs the full picture instead of one failure at a time — both share the identical extracted fixpoint engine, so a build-time rejection and a live diagnostic can never silently disagree about the same puzzle. A puzzle-content import path (the editor's JSON import) that shares an underlying auto-detection helper with a build-time loader (`parsePuzzleSource`, moved to `shared` from being private to `site`'s loader) deliberately does *not* also inherit that loader's fairness gate — importing an already-broken puzzle file must still succeed, since the point is reopening it specifically to fix it with the new solvability button, not blocking that repair workflow (see `.vibe/decisions/040-editor-solvability-diagnosis-and-json-import.md`).
- An automatic single-cell fix search (the editor's solvability-check "also try…" suggestion) is scoped by two independent hard caps decided from real measured evidence, not a guess: a small ambiguous-area-size ceiling (grounded in testing the exact two puzzles once removed for requiring guessing — neither had any single-cell fix among ~130/~70 candidates tried, confirming a spread-out ambiguity has none to find) and a fixed total-attempts ceiling on top of it (grounded in real per-puzzle solvability-check timings, since every attempt re-runs a full check) — see `.vibe/decisions/041-solvability-single-cell-fix-suggestion-bounded.md`.
- Permanent row/column number headers added to an existing ARIA grid (the editor's canvas) live inside the *same* `<table>` as native `<thead>`/`<th scope>` cells with the matching `columnheader`/`rowheader` ARIA roles, rather than a separately-positioned overlay — this way the numbering scales in lockstep with the grid's own font-size-driven fit at every size for free, with zero synchronization logic. A header cell's number glyph sits in a nested `<span>` carrying its own smaller `font-size`, so the header's own box (`2em`, matching a data cell's box exactly) is sized against the *inherited*, unshrunk font-size rather than its own — putting a smaller `font-size` directly on the sizing element itself would have shrunk its `2em` box too, silently misaligning headers from the grid at every scale. New headers are also reflected in a data cell's own aria-label (a "Row R, column C" prefix, substituted the same way the pre-existing `{number}` token is) rather than left visual-only, once accessibility review flagged that as creating an equity gap the brief hadn't actually intended — see `.vibe/decisions/042-editor-grid-row-column-numbering.md`.
