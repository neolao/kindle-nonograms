## Observed patterns
- The project no longer ships a runtime server — it is being rebuilt as a static site.
- Client code guards DOM access behind `typeof document !== "undefined"` so pure logic stays testable outside a browser.
- Domain types live in `shared` and are meant to be imported by both the client and, eventually, the static-site generator.
- Clues are never stored — they are always derived on demand from a puzzle's solution grid.
- Browser-API-dependent client tests opt into a per-file `// @vitest-environment jsdom` pragma rather than switching the whole suite's default environment.
- Puzzle source files are auto-detected by shape (native vs. reMarkable export) rather than by a format tag, and a source file's id always comes from its filename, never from content.
- Rendered puzzle pages inline all their own CSS in a `<style>` block (no external stylesheet exists yet) and never encode information by color alone, since Kindle's e-ink screens are often grayscale.
- Client-side updates to the puzzle grid touch only the single cell that changed, never rebuilding the grid, to avoid a visible redraw on Kindle's slow e-ink refresh.
- Generated pages keep their visible markup solution-blind but embed the full puzzle data as JSON regardless, since the site has no backend to hide solutions behind anyway.
- Every generated page loads the same client bundle; each hydration script self-detects whether its expected markup is present and no-ops otherwise, rather than the build shipping a separate bundle per page shape. Each page shape has its own distinct, unambiguous marker for this (the embedded `#puzzle-data` script for the puzzle page, the embedded `#puzzles-data` script for the library page, a `data-role="editor-page"` marker for the editor) — a marker two page shapes could both satisfy (e.g. just "an `<h1>` exists", or, once the editor's own canvas started rendering a real `<table>` too, a bare `<table>`) caused a real double-hydration bug once tried, which is exactly why the puzzle page's own marker was moved off `<table>` and onto its embedded JSON script instead.
- Filled grid cells and color-swatch buttons render as plain solid-color squares — no shape glyph is drawn on top, only the active swatch carries a checkmark, whose color is picked by actual WCAG contrast ratio against both black and white (not a fixed luminance threshold) so it stays legible against any arbitrary palette color.
- Any UI text meant to be retranslatable client-side carries a `data-i18n` key holding its translation key; a single generic `applyLocale(locale)` call re-walks every `[data-i18n]` element in the page and swaps its text in place, whether the element came from server-rendered HTML or was built later in client JS.
- Visual design tokens (colors, spacing, border widths, font stack) are plain TS constants interpolated into literal CSS strings at build time, never CSS custom properties (`var()` support on Kindle's old WebKit is uncertain).
- A block element with `overflow:hidden` clips nothing unless it also has an explicit bounded size — `max-width`/`max-height` set from a real measurement is what turns that CSS declaration into an actual fail-safe.
- A `<table>`'s natural size is measured directly off the `<table>`, never off a wrapping `<div>` around it — a `<div>` stretches to its container's width by default regardless of content, which would misreport a small puzzle's true size.
- Chrome spacing (margins/padding/borders on headings, toolbars, banners, the header row) is always applied to individual elements, never to `body` or the puzzle page's `.grid-wrapper` — the grid-fit measurement reads the raw viewport size, so any spacing added to an ancestor of the wrapper would silently make it overflow its computed cap.
- The site deliberately uses a three-accent color system (superseding an earlier single-muted-accent rule — see `.vibe/decisions/013-three-accent-cabinet-reskin.md`): each accent has one fixed, reused role across both pages (navigating away/active toggle, the primary in-puzzle action, "completed" shared by the win banner and the library's solved stamp so the two visibly connect) so the palette reads as a deliberate system, plus separate decorative-only cycling on the marquee dot row that carries no meaning (the library card's top stripe used to cycle the same way but now reflects the puzzle's own palette instead — see `.vibe/decisions/015-library-card-stripe-reflects-palette.md`). The puzzle grid's own rendering (clue borders, cell/palette colors) is never touched by these accents, so it stays the calmest, most legible element on the page regardless of how bold the chrome around it gets.
- A second, monospace font layer is applied only to headings/buttons/badges/section labels, never body copy or fine print — at Kindle's small rendering sizes monospace looks cramped for anything longer than a short label.
- A static link meant to work before/without JavaScript is rendered server-side, never built by a hydration script — a hydration-built control is invisible until hydration finishes and unusable if it never runs at all.
- A derived visual (a rendered preview, not the raw embedded solution JSON) that would spoil a puzzle before it's solved is built client-side only, on confirmed proof of having solved it — server-rendering it hidden-until-revealed still leaves it sitting in the page's HTML source, which is a real difference from the already-accepted "full solution is embedded as JSON anyway" baseline.
- Fixed-size decorative UI (a thumbnail box) keeps an identical footprint across its placeholder and revealed states, swapping only inner content, so a state change never shifts surrounding layout.
- A "pressed in" button look (an offset shadow that flattens) is applied as a discrete style swap on `:active` and on `aria-pressed="true"` alike — never a `transition` — so a held-down button and a persistently active toggle read the same way without violating the no-animation e-ink constraint.
- Corner radius is a single shared token applied everywhere in the visual system, including elements the grid-fit calculation measures (the puzzle grid's own frame) — safe because border-radius is purely decorative and never affects box size or layout measurement, unlike padding/margin/border-width.
- Two chrome elements that need their own separate bordered boxes (the puzzle page's control panel and its grid frame) are kept as sibling elements, never one nested inside the other — nesting would force a shared padded container, which is exactly what the grid-fit measurement can't tolerate.
- Chrome height on the puzzle page specifically is treated as a real, measured budget, not an aesthetic afterthought — a decorative element kept on the library page (the dot row) is dropped on the puzzle page alone, since headless-browser measurement showed the combined header chrome eating over a third of a small Kindle-sized viewport before the grid even started. Two rows that can share one line (a heading and its adjacent controls) are merged rather than stacked, with `flex:1;min-width:0` plus `text-overflow:ellipsis` on the heading so a long title truncates instead of colliding with or pushing those controls — `min-width:0` specifically because a flex item's default `min-width:auto` otherwise prevents it from ever shrinking below its content's natural width, silently defeating the ellipsis. The same `min-width:0` + single-line-ellipsis pattern is reused for the library page's row link, so a long/UUID-fallback puzzle name truncates instead of wrapping and inflating just that one card's height relative to its neighbors.
- An icon-only control never relies on `aria-label` alone for its accessible name: the icon glyph sits in its own `aria-hidden="true"` element, paired with a `.sr-only`-clipped span carrying the full translated label — visually hidden via the standard clip technique (never `display:none`/`visibility:hidden`, which would also strip it from the accessibility tree), so the same generic `[data-i18n]`-walking translation mechanism keeps working unchanged on it.
- A plain Unicode glyph used for a functional icon is deliberately picked from a widely-supported block (Dingbats/Arrows) already proven safe elsewhere in the app, never a rarer symbol block or a color emoji — old e-ink WebKit's font coverage for anything outside the most common ranges is a real, unverifiable-in-advance risk (a silent blank/tofu box), so an imperfect-but-safe metaphor beats a perfect-but-risky one.
- Buttons that represent one combined action (e.g. choosing a fill color as part of filling) are wrapped in their own small bordered sub-container nested inside the toolbar, styled with softer tokens (`panelEdge`/`paper`) than the app's main panel treatment (`border`/`panel`) — a deliberately lighter visual weight so a nested grouping cue never competes with the page's actual panels.
- The grid-fit shrink floor is tuned to actually prevent a wide puzzle from being clipped on a narrow real screen, not just to protect legibility — a silently missing cell or clue is treated as strictly worse than a smaller-than-ideal one. Border widths stay fixed px (not `em`) even though the rest of the grid scales by `font-size`, so real rendered width at very small scales drifts slightly from the pure linear prediction — a minor effect the floor's own safety margin already tolerates at realistic screen widths.
- A puzzle's palette hex values, when interpolated into a page's shared `<style>` block, are validated against a strict hex-color pattern first, falling back to black for anything that doesn't match — required wherever one page's stylesheet folds together data from more than one puzzle (e.g. every card on the library page), since an unvalidated value there is a CSS-injection surface in a way a single curated puzzle's own page isn't.
- Client-side visibility toggling (a solved badge, a filtered-out library row) always sets the `hidden` boolean property on the existing element rather than removing or reappending it — every other id-based hydration lookup keeps finding the element regardless of its current visibility state.
- A row's own filterable/derivable properties (size bucket, color type) are computed once server-side and read back client-side as plain `data-*` attributes, rather than recomputed in the browser from the embedded puzzle JSON.
- Puzzle content validation (fairness/solvability, duplicate detection) lives in `shared` as pure functions and is wired into `site`'s loading path, never into `createPuzzle` itself — structural validation (`createPuzzle`) and content-quality validation are kept as separate, independently callable checks.
- An expensive-looking per-line check (e.g. a nonogram line solver) is implemented as a dynamic-programming feasibility oracle over the line, never by enumerating and materializing every possible placement — the latter blew the heap on a real 45×45 puzzle during this project's own development.
- A contributor-facing authoring tool (the puzzle editor) deliberately does not follow the play page's "repaint only the changed cell" discipline — that constraint exists for Kindle's slow e-ink refresh, which doesn't apply to a page run in a normal desktop browser, so the editor fully re-renders its palette and grid after every edit instead, simple over clever.
- A page whose own interactive script can build a `<table>` dynamically (the puzzle editor's grid canvas) is imported last in the shared client entry point, after every other hydration script that self-detects by checking for an existing `<table>` — importing it earlier would let its freshly-built table falsely satisfy that other check before the dynamically-built one even exists at parse time.
- A privileged GitHub Actions workflow triggered by `workflow_run` (needed whenever a low-privilege `pull_request` job must hand off to something with write access) never trusts a PR number carried inside an artifact the low-privilege job produced without independently cross-checking it against GitHub's own commit→PR association API first — the artifact is PR-controlled content, so its declared identity has to be confirmed, not assumed.
- `git add -A -- <pathspec>` hard-errors when the pathspec matches nothing left to add (an empty directory, or a deletion an earlier call in the same run already fully staged) — this is treated as "nothing new to stage" via a try/catch around the `add` call itself, not a `git status` pre-check, since status can still report something "pending" in a state `add` has genuinely nothing left to do for.
- A binary encoder needing only a narrow, well-defined format (e.g. a PNG with a single filter type and no interlacing) is written directly against Node's own built-ins (`node:zlib`'s `deflateSync`/`crc32`) rather than pulling in an image/canvas library, when the full format's generality isn't needed.
- The site's first external (leaves-the-app) link states that fact in its visible wording itself (naming the destination, e.g. "on GitHub") plus a trailing "↗" glyph — never color alone, and never only `target="_blank"` with no visible cue, since the whole point is a tap-only e-ink visitor knowing before tapping that it leaves the Kindle browser.
- Every adaptive chrome layout in the site (header row, filter bar, and now the library footer) stacks on a narrow screen via a plain `display:flex;flex-wrap:wrap` container, never an `@media` breakpoint — the project has never introduced one, on the reasoning that flex-wrap alone, verified by rendering at a real narrow width, already produces an acceptable stacked layout.
- A CSS class rule that sets its own `display` value on an element also toggled via the `hidden` attribute is scoped `.foo:not([hidden])`, never plain `.foo` — a class selector and the `[hidden]` attribute selector share the same specificity, so a plain `.foo{display:...}` declared later in the stylesheet silently wins over `[hidden]{display:none;}` regardless of the attribute's actual value, defeating the hide. Caught by driving the built site in a real browser (jsdom-based tests only assert the `hidden` DOM property, never the resulting computed style, so they can't catch this).
- When `site`'s `build.ts` calls Vite's programmatic `build()` with a `configFile` from `packages/client`, options that default relative to `root` (e.g. `publicDir`) still resolve against `process.cwd()` — not the config file's own directory — since `root` itself isn't overridden. Any option meant to reach into `packages/client` from that call has to be passed explicitly with an absolute path; relying on Vite's own default silently no-ops instead of erroring.
- An editor action that outright replaces a whole chunk of state (not a merge, not a single field) asks for confirmation via the browser's native `confirm()` only when there's actual content at risk of being lost — an already-empty target applies the result directly, matching every other editor action's own immediate-apply-no-undo model, so a genuinely destructive action gets a guard the rest of the editor doesn't need without over-prompting when nothing would actually be lost.
- A control that reads another live-editable field's value as part of its own action (e.g. the image importer reading the grid's width/height) always reads it at the moment the action actually runs, never at an earlier "setup" moment (e.g. when a file was picked) — those fields stay editable in between, so reading early can silently use a stale value.
- DOM-only glue that a project's test environment can't meaningfully exercise (e.g. real `<canvas>`/`Image()` pixel decoding — jsdom doesn't implement it) is kept in its own small, thin module, isolated from the pure/testable logic it feeds, and documented as verified by driving a real browser instead of by unit tests — the same boundary already drawn around `publish-preview-cli.ts`, now reused for `decodeImageFile.ts`.
- A privileged script that both reads a live external list (e.g. currently open PRs) and reads/mutates a stored state it's about to diff against that list (e.g. checking out a branch to inspect it) always does the live read *first* — any change that lands in the gap between the two reads then belongs, by construction, to whichever side already reflects it, so the gap can only ever make the script more conservative, never cause it to act on something that changed underneath it. Reordering these two reads would reopen a real race window rather than just being a style choice.
- Every page's default chrome (the puzzle page's toolbar/win banner/storage warning, the library page's filters/pagination, the editor's palette/toolbar/canvas) is now baked directly into static HTML in its exact default shape by `site`'s `render*Page()` functions, rather than built from scratch by client hydration on first load; hydration only locates that markup by its `data-role` attributes and attaches behavior. A handful of controls whose true state is only known client-side (the win banner, solved badges) are still corrected by a synchronous, blocking check before the page is perceived as painted, rather than through a visible loading state — any visible post-paint transition (a dimmed→active flip, a wrong→right flash) works directly against the e-ink no-animation constraint (see `.ux/decisions/001-frozen-chrome-blocking-reconciliation.md`).
- The default UI state values a page's static rendering and its hydration-time rebuild must agree on (the play page's starting mode/active color, the editor's starting grid size/palette/tool, puzzles shown per library page before pagination) live in one shared module (`shared`'s `uiDefaults.ts`) rather than being declared independently on each side, so the two can never silently drift into disagreeing about what "default" means.
- A hydration test's DOM fixture is built by calling the real `site` package's `render*Page()` function and extracting its `<body>` markup (`client`'s `htmlFixture.ts`), never a hand-retyped copy of that markup — the latter can silently drift out of sync with what the renderer actually emits once the two evolve independently.
- A WCAG-contrast color-pick helper needed identically by both a build-time static renderer and a runtime hydration rebuild (`contrastingTextColor`) lives in `shared`, not in whichever side happened to need it first — moved there from `client` once `site` also needed to bake the same computed swatch color into static HTML, so the two can never pick different colors for the same input hex.
- A function that used to degrade a failure silently (returning `void`) switches to reporting it back as a boolean once a caller actually needs to react to that specific failure — `saveProgress` now returns `false` on a failed write so the play page can show a one-time warning, while every other storage helper in the same client (`loadProgress`, the locale cookie read/write) still swallows silently, since nothing yet consumes their failure signal.
- A one-time, dismissible, per-page-view warning (shown once even if the underlying failure recurs) is tracked by a plain in-memory boolean, set synchronously on first occurrence before anything else runs, so two occurrences in the same tick can't both slip through; dismissing it early never resets that flag, so a later recurrence doesn't bring the warning back. No new storage primitive is introduced for a scope this narrow — the in-memory flag already matches every other piece of transient play state (see `.vibe/decisions/020-save-failure-warning-scoped-to-page-view.md`).
