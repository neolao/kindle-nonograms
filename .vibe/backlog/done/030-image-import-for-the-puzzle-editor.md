# Image Import for the Puzzle Editor

## Description
Extend the puzzle editor ([[029-web-based-puzzle-editor]]) with an "import image" action: a contributor picks a local image, chooses target grid dimensions and a color count, and gets a starting `palette`/`cells` grid generated by downsampling and quantizing the image — which they then refine by hand in the freehand editor before exporting. This saves re-drawing existing pixel art or sketches cell by cell.

## Acceptance Criteria
- [ ] The editor page gains a file input accepting common raster formats (PNG/JPG), decoded fully client-side via `<canvas>`/`Image()` — nothing is uploaded anywhere, consistent with the project's no-server model.
- [ ] The user specifies target grid width/height before import; the image is downsampled to that resolution via block-averaging (not naive nearest-neighbor), so a single noisy pixel can't dominate a whole cell.
- [ ] The user picks a target palette size; a simple, dependency-free color quantization step (e.g. median-cut) reduces the downsampled image to that many representative colors, producing the `palette` array plus a `cells` grid of indices into it.
- [ ] A configurable background color maps to `null` cells instead of a palette entry, so imported puzzles get real blank space rather than every pixel being "filled" — matching how hand-drawn puzzles treat background.
- [ ] Import populates the same editor state as freehand mode (width/height/palette/cells) and switches into it — the result is immediately editable by click-painting, not a read-only preview.
- [ ] The pure quantization/downsampling logic (no DOM/canvas) lives in a testable module (e.g. `packages/client/src/imageQuantize.ts`) with unit tests: known small pixel grids in → expected palette/cells out, including edge cases with fewer distinct colors than the requested palette size and with a fully uniform image.

## Notes
Depends on [[029-web-based-puzzle-editor]]'s grid/palette/cells state existing to import into — this reuses that state rather than building a separate flow. Keep the quantization algorithm simple and dependency-free (no external image-processing library), matching the project's minimal-footprint style; a naive median-cut is enough quality given a nonogram's small color counts. Worth checking during implementation whether `main.ts`'s per-page dispatch already keeps unrelated hydration code out of the play/library bundles, and following that existing pattern so this import logic doesn't bloat those bundles.
