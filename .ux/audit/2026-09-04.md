# UX audit — 2026-09-04

- **Scope:** full UI layer — `packages/site/src` (server-rendered pages) and `packages/client/src` (hydration bundle): library, puzzle/play page, editor.
- **Captures:** `.ux/captures/audit-2026-09-04/` — library (desktop + Kindle-width viewports, empty-filter state), puzzle page (mono + multi-color, solved state), editor (desktop + Kindle-width). App was built (`npm run build`) and served locally for real, interactive captures (Playwright), including a keyboard-only Tab-order probe on the puzzle page.
- **Agents run:** heuristic pass (this session) + `ux:review-states`, `ux:review-accessibility`, `ux:review-content`, `ux:review-consistency`, `ux:review-visual` (conformance skipped — no `.ux/flows`/`.ux/screens` specs exist yet).

## Summary

Findings: 32 (High: 4, Medium: 20, Low: 8)

The most consequential problems cluster around three things: interactive chrome (toolbars, banners, pagination, the whole editor UI) is built entirely by JavaScript with no server-rendered placeholder, so every page load visibly pops in — a direct hit on the app's own "slow e-ink refresh, no animations" constraint, felt by the player on every single visit. Second, several feedback paths actively mislead or go silent: "Check" claims wrong cells were "fixed" when they were only cleared, and a failed `localStorage` write during play loses a player's progress with zero warning. Third, the editor (the contributor's only tool) has the roughest edges — untranslated despite the app's bilingual promise, raw English/browser errors surfaced verbatim, and several controls (palette swatches, color inputs) that are functionally identical to a screen reader. Per this session's scoping decision, the puzzle grid's total lack of keyboard support is recorded as a known gap but excluded from prioritization (no accessibility target is declared for this Kindle-touch-first app).

| F1 | High | visual / states | `renderLibraryPage.ts`, `renderPuzzlePage.ts`, `renderEditorPage.ts` + matching `hydrate*.ts` | No page ships server-rendered chrome for its toolbar, win banner, filters/pagination, or (on the editor) the whole palette/canvas UI — all of it is built and inserted only once hydration JS runs, so every load visibly pops in. | F12 | Medium | states | `packages/client/src/hydrateEditorPage.ts:483-500` | Typing an invalid width/height (zero, negative, non-numeric) silently reverts the field with no explanation, unlike every other editor action which reports into `elements.error`. | Write a message to `elements.error` ("Width/height must be a whole number greater than 0") before reverting. |
| F13 | Medium | states | `packages/client/src/hydrateEditorPage.ts:529-587`; `decodeImageFile.ts:16-60` | Image import has no timeout — if the browser's `<img>` never fires `onload`/`onerror`, import controls stay disabled indefinitely with no cancel/retry short of reloading. | Race the decode promise against a timeout (e.g. 15s) that rejects with a clear message. |
| F14 | Medium | states | `packages/client/src/hydrateEditorPage.ts:589-607` | A successful export only clears the error field and silently triggers a download — no visible confirmation of the terminal action of the whole editor flow. | Show a brief confirmation ("Exported `<filename>`.json — download started.") after a successful export. |
| F15 | Medium | accessibility | `packages/client/src/hydratePlayPage.ts:221-232` | Color swatch buttons for picking the active fill color have no accessible name at all — a screen reader announces an unlabeled button with no way to tell which color it selects. | Give each swatch an `aria-label` naming or numbering its color. |
| F16 | Medium | accessibility | `packages/client/src/hydrateEditorPage.ts:222,239` | Every palette swatch gets the identical `aria-label="Select color"`, and every palette color `<input type="color">` gets the identical `aria-label="Edit color"` — indistinguishable to a screen reader across an entire palette. | Differentiate by index/hex, e.g. `"Select color 2 (#3388cc)"`. |

**Known gap, out of scope for this audit's prioritization** (per this session's clarification — no accessibility target is declared, and the app's primary device is a touchscreen): the puzzle grid on the play page has no keyboard support whatsoever — confirmed by tabbing through the puzzle page, where focus skips straight from the Check button back to `<body>`. Already recorded in `.ux/inventory.md` → Known gaps.

## Suggested next designs

1. `/ux:design F1` — server-render (or height-reserve) the toolbar/banner/pagination/editor chrome to remove the pop-in that hits every page load on the app's own slow-refresh e-ink target.
2. `/ux:design F5` — wire the editor into the existing i18n pipeline and add its language switcher, closing the app's only fully-untranslated page.
3. `/ux:design F2` — design the failure-feedback path for `saveProgress`, so a lost save is never silent.
